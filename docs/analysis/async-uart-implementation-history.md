## 1. 项目目标与背景

**项目目标**：为 StarryOS 实现高性能异步串口通信（AsyncUart）

**技术目标**：
- 波特率支持：115200 bps（可扩展至 1 Mbps）
- RX 延迟：P50 < 500 µs, P99 < 2 ms
- CPU 利用率（空闲）：0%（中断驱动，无空转）
- 吞吐量：> 90% 线速

**初始状态**：
- Console（axhal::console）使用同步阻塞 TX（polling 空转）
- Console RX 中断驱动（IER::DATA_READY）
- Console UART 配置：只使能 RX 中断，禁用 TX 中断

## 2. 实现策略演进时间线

### 2.1 第一阶段：渐进式集成方案（feat/uart-async 分支）

**时间范围**：2026-05-24 ~ 2026-05-28

**策略核心**：复用 Console UART 初始化，渐进式替换 Console 软件路径

**Milestone 规划**：
- M0-M2：基础架构验证（中断 + Ring Buffer + VFS）
- M3：AsyncUart 替换 Console（关键替换点）
- M4-M6：性能优化 + 真板验证

**关键设计决策**：
1. Console 与 AsyncUart 共用 UART 硬件（UART0）
2. Console TX 同步阻塞 → AsyncUart TX 异步（M3 替换）
3. IRQ waker 共存机制（register_irq_waker 支持）

**实现成果**：
- ✅ M0-M2 完成：ConsoleDriver、RX copier、VFS 集成
- ❌ M3 替换失败：IRQ 风暴 + TX busy-loop

**失败症状**（ADR-019 / learned.md L78）：
```
1. IRQ 风暴：RX-COPIER 和 tty-reader 快速循环唤醒
2. TX busy-loop：TX FIFO 满，UART 状态异常（LSR=0x00）
3. UART 硬件未正常发送数据：FIFO 满后 retry 无效
```

**失败根因**：
- Console UART 状态不兼容 AsyncUart（Console 只使能 RX 中断）
- 未验证 UART 状态就开始集成（缺少 IIR/MCR/LSR 调试）
- THR_EMPTY 状态理解错误（learned.md L80）

**教训**：
- ❌ 未验证硬件状态就开始集成
- ❌ 假设 Console 初始化后的 UART 状态正常
- ❌ ADR-018 战略转向过于激进（未充分验证可行性）

## 3. 关键阻塞发现历程

### 3.1 第一次阻塞：内核上下文 UART MMIO 权限问题

**发现时间**：2026-05-28（P1.3 实现）

**症状**（learned.md L113）：
```
- Page Fault @ 0x1000001c（物理地址未映射）
- StoreFault @ 0xffffffc01000001c（虚拟地址无写入权限）
- LoadFault @ 0xffffffc010000008（虚拟地址无读取权限）
```

**根因**：
- axplat 在 boot 阶段映射 UART MMIO（完整权限）
- 内核启动后（entry.rs init），MMIO 权限被限制（只读或禁止）
- UART MMIO 地址 0x10000000 在内核启动后无法访问

**尝试方案**：
1. 使用物理地址 → Page Fault（未映射）
2. 使用 phys_to_virt 转换 → StoreFault/LoadFault（权限限制）
3. MMIO write_volatile 直接写入 → StoreFault（权限限制）

**策略调整**（ADR-022）：
- 完全放弃在内核启动后访问 UART 寄存器
- 依赖 axplat 的 UART 配置
- 测试 ISR 上下文访问权限（关键验证）

---

### 3.2 第二次阻塞：ISR 上下文 UART MMIO 权限问题

**发现时间**：2026-05-29（P2.1 测试）

**验证过程**：

**Step 1：ISR handler 实现**
- 创建 kernel/src/drivers/isr.rs
- 实现 uart_isr_handler（尝试读 UART ISR 寄存器）

**Step 2：ISR handler 注册**
- 在 entry.rs init() 中调用 `axhal::register_irq_hook(uart_isr_handler)`
- 内核启动成功，ISR handler 注册成功

**Step 3：ISR 执行验证**
```
[kernel] UART ISR handler registered
[UART ISR] ISR handler called (IRQ ...)
[UART ISR] Attempting to access UART registers...
[UART ISR] UART lock acquired, attempting to read ISR register...
```

**Step 4：UART 访问失败**
```
panicked at ... Exception(LoadFault) @ 0xffffffc08026c9ea, stval=0xffffffc010000008
```

**关键结论**（ADR-023 / learned.md L116）：
- ISR handler 成功注册并执行 ✅
- ISR 尝试读 UART ISR 寄存器触发 LoadFault ❌
- MMIO 权限限制对**所有上下文**都生效（内核 + ISR）
- UART 虚拟地址 `0xffffffc010000008`（ISR 寄存器）无法访问

**最终结论**：
- ✅ 证明了不彻底更改底层支持就无法使用异步串口
- ❌ 原设计（ISR 使能 TX 中断）完全不可行
- ❌ AsyncUart 异步 TX 路径无法实现

## 4. 问题分析与根因追溯

### 4.1 Console 与 AsyncUart 数据竞争根因

**Console 架构约束**（learned.md L88）：
- Console 是外部 crate（axplat），无法修改其实现
- Console TX 使用同步阻塞（polling 空转等待 THR_EMPTY）
- Console RX 中断驱动，但 UART 配置不透明

**数据竞争类型**：
1. **TX 数据竞争**：Console TX（同步）与 AsyncUart TX copier 同时写 THR
2. **IRQ waker 冲突**：Console tty-reader 与 AsyncUart copier 竞争 IRQ 10
3. **UART 重初始化冲突**：AsyncUart 重初始化破坏 Console 配置

**根因**：
- Console UART 配置状态不明确（外部 crate 无法查询）
- Console 禁用 TX 中断（IER::THR_EMPTY 未使能）
- AsyncUart 需要 TX 中断（无法在 ISR 中使能）

---

### 4.2 UART MMIO 权限问题根因

**Boot 阶段架构**：
```
axruntime::init()
  → axhal::init()
    → axplat::init()
      → axplat-riscv64-qemu-virt console.rs: UART MMIO mapping
```

**MMIO 映射策略**（推测）：
- axplat 在 boot 阶段映射 UART MMIO（完整权限：RW）
- axplat 创建 MmioSerialPort 结构，封装 UART 操作
- axplat 提供 console::read_bytes/write_bytes API

**权限限制机制**（推测）：
- 内核启动后（entry.rs init），axplat 可能：
  1. 限制 UART MMIO 权限（只读或禁止）
  2. 或使用 PMP (Physical Memory Protection) 限制访问
  3. 或使用页表权限位限制

**验证证据**：
- 内核上下文访问 UART → LoadFault/StoreFault
- ISR 上下文访问 UART → LoadFault（`stval=0xffffffc010000008`）
- phys_to_virt 转换后虚拟地址无权限

**架构约束**：
- axplat 是外部 crate（crates.io），无法修改
- axplat 的 MMIO 映射策略不透明（无文档）
- 无法在 kernel 层绕过 axplat 的权限限制

---

### 4.3 ISR 测试验证的意义

**验证目的**：
- 测试 ISR 是否有不同的 MMIO 权限映射
- 验证原设计（ISR 使能 TX 中断）是否可行

**验证方法**：
- 实现最小 ISR handler（uart_isr_handler）
- 尝试读 UART ISR 寄存器
- 观察是否触发异常

**验证结果**：
- ISR handler 成功执行（说明 ISR 上下文正常）
- ISR 访问 UART 失败（说明 MMIO 权限限制存在）
- LoadFault @ stval=0xffffffc010000008（ISR 寄存器地址）

**关键意义**：
- 排除了 ISR 有特殊权限的可能性
- 证明了 MMIO 权限限制对所有上下文都生效
- 确认了原设计完全不可行

## 5. 后续策略与架构影响

### 5.1 可行方案评估

**方案 A：Polling TX（同步阻塞）**
- 优点：简单可行，无需修改外部 crate
- 缺点：牺牲异步性能，TX 路径 CPU 空转
- 适用：RX 中断驱动 + TX polling 模式（半异步）
- 风险：中等（性能受限）

**方案 B：Boot 阶段修改 UART 配置**
- 优点：可实现完整异步 TX
- 缺点：需要修改 axplat（外部 crate），复杂度高
- 适用：彻底重构底层架构
- 风险：高（维护成本高，需上游协调）

**方案 C：完全依赖 Console（回退 feat/uart-async）**
- 优点：Console RX 已中断驱动，功能可用
- 缺点：放弃 AsyncUart 独占 UART 的目标
- 适用：渐进式集成方案（已失败）
- 风险：低（放弃原目标）

---

### 5.2 对 StarryOS 架构的影响

**短期影响**：
- AsyncUart 实现暂缓
- Console 仍是唯一的串口驱动
- TX 路径性能受限（同步阻塞）

**长期影响**：
- 需评估修改 axplat 的可行性（方案 B）
- 或接受 Polling TX 方案（方案 A）
- 需与上游 axplat 项目协调（方案 B）

**架构反思**：
- 外部 crate 的架构约束对整个系统都有影响
- 需在设计初期验证关键假设（MMIO 权限）
- 需明确外部 crate 的接口和限制

## 总结

AsyncUart 异步串口实现历经两个分支的探索，最终发现关键架构约束：

**feat/uart-async 分支**：
- 渐进式集成方案（复用 Console）
- M3 替换失败（IRQ 风暴 + TX busy-loop）
- 发现 Console 与 AsyncUart 数据竞争风险

**feat/uart-async-dev2 分支**：
- 完全剔除 Console 方案（从零开始）
- 发现内核 UART MMIO 权限问题
- ISR 测试验证失败（LoadFault）

**最终结论**：
- ✅ ISR handler 成功注册并执行
- ❌ ISR 无法访问 UART 寄存器（MMIO 权限限制）
- 💡 不彻底更改底层支持就无法使用异步串口

**关键意义**：
- 排除了 ISR 有特殊权限的可能性
- 确认了 axplat 的架构约束无法绕过
- 为后续架构决策提供了明确的验证依据

**后续决策**：
- 方案 A：Polling TX（简单可行）
- 方案 B：修改 axplat（复杂高风险）
- 方案 C：依赖 Console（放弃目标）

- learned.md：踩坑档案（L113-L116）
- architecture.md：ADR（ADR-020 ~ ADR-023）
