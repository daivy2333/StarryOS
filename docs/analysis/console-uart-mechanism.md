## 1. Console UART 硬件配置

### 1.1 MMIO 地址与 IRQ 号

Console 使用的 UART 硬件配置：

| 参数 | 值 | 来源 |
|------|-----|------|
| **MMIO 基地址** | 0x10000000 | axplat-riscv64-qemu-virt axconfig.toml |
| **IRQ 号** | 10 (0x0a) | axplat-riscv64-qemu-virt axconfig.toml |
| **寄存器 stride** | 4 | RISC-V MMIO 标准（每个寄存器占 4 字节） |

**关键寄存器偏移**（相对于 MMIO 基地址 × stride）：

| 寄存器 | 偏移 | 功能 | 读/写 |
|--------|------|------|-------|
| THR/RBR (DATA) | 0 | 发送/接收数据寄存器 | 读: RBR，写: THR |
| IER | 1 | 中断使能寄存器 | RW |
| ISR | 2 | 中断状态寄存器（IIR） | R |
| FCR | 2 | FIFO 控制寄存器 | W |
| LSR | 5 | 线状态寄存器 | R |

### 1.2 UART 寄存器位定义（uart_16550 crate）

**IER（Interrupt Enable Register）**：
- `IER::DATA_READY` (bit 0): 使能 RX 数据中断
- `IER::THR_EMPTY` (bit 1): 使能 TX 空中断
- `IER::RECEIVER_LINE_STATUS` (bit 2): 使能接收线状态错误中断
- `IER::MODEM_STATUS` (bit 3): 使能调制解调器状态中断

**LSR（Line Status Register）**：
- `LSR::DATA_READY` (bit 0): RX FIFO 有数据
- `LSR::THR_EMPTY` (bit 5): TX FIFO（发送保持寄存器）空
- `LSR::TEMT` (bit 6): 发送器完全空（THR + TSR）
- 其他位：错误标志（Overrun/Parity/Framing）

**ISR（Interrupt Status Register）**：
- `ISR::INTERRUPT_STATUS` (bit 0): `0` 表示有中断待处理，`1` 表示无中断
- `ISR::interrupt_type()`: 返回 `InterruptType` 枚举
  - `ReceivedDataReady`: RX 数据就绪
  - `TransmitterHoldingRegisterEmpty`: THR 空
  - `ReceptionTimeout`: RX 超时
  - 其他类型：LineStatus/ModemStatus/DMA

## 2. Console TX 阻塞机制

### 2.1 同步阻塞忙等待实现

Console 的 TX 路径使用**同步阻塞忙等待**：

**调用路径**：
```
用户 write()
  → Console.write_at()
    → TtyWrite::write() (Console struct)
      → axhal::console::write_bytes(buf)
        → [外部 crate: axplat-riscv64-qemu-virt]
          → 逐字节写 THR，等待 THR_EMPTY
```

**阻塞等待实现**（推测，基于 UART 标准）：
```rust
// axplat-riscv64-qemu-virt console.rs (外部 crate)
pub fn write_bytes(buf: &[u8]) {
    for byte in buf {
        // 忙等待 THR_EMPTY 标志（LSR bit 5）
        while !THR_EMPTY {
            // CPU 空转，等待硬件发送完成
        }
        // 写 THR 寄存器
        write_thr(*byte);
    }
}
```

**性能影响**：
- CPU 空转：发送每个字节时等待 THR_EMPTY 标志
- 阻塞时间：取决于波特率和 FIFO 状态
  - 115200 bps: 每字节 ~87 µs
  - FIFO 满（16 字节）时等待更长时间
- **不使用 THRE 中断**：纯 polling 模式

**关键发现**：Console TX 路径**不使用中断**，完全同步阻塞。这是导致与 AsyncUart TX copier 数据竞争的根源。

## 3. Console RX 中断驱动机制

### 3.1 register_irq_waker 使用

Console 的 RX 路径使用**中断驱动**：

**调用路径**：
```
UART RX 中断 (IRQ 10)
  → PLIC claim
    → dispatch_irq(10)
      → IRQ_WAKERS[10].wake_by_ref()
        → tty-reader 任务唤醒
          → Console.read_bytes()
            → 读 RBR 寄存器
              → push rx_buf
```

**register_irq_waker 注册**（ntty.rs:38）：
```rust
ProcessMode::External(Box::new(move |waker| register_irq_waker(irq, &waker)))
```

**tty-reader copier 任务**（ldisc.rs）：
```rust
poll_fn(|cx| {
    // 1. 读 Console RX 数据
    let n = reader.read(&mut read_buf);

    // 2. 处理数据（行规则、信号）
    // ...

    // 3. 注册 IRQ waker
    register_irq_waker(irq, cx.waker());

    // 4. 返回 Pending（等待下次中断）
    Poll::Pending
})
```

### 3.2 IRQ Waker 共存问题

**关键问题**：当前框架每个 IRQ 只支持**一个 waker**（interrupt-framework.md 3.3 节）。

**冲突风险**：
- Console 的 tty-reader 已注册 IRQ 10 waker
- AsyncUart 的 RX/TX copier 也需注册 IRQ 10 waker
- **两者冲突**：无法分别唤醒 RX 和 TX copier

**可能的解决方案**（见 interrupt-framework.md 4.3 节）：
- 使用 `AtomicWaker` + ISR 读取 ISR 寄存器区分中断类型
- ISR 中根据中断类型唤醒不同的 waker

## 4. tty-reader 与 Console 协作关系

### 4.1 Console 结构体

**定义**（ntty.rs:14-24）：
```rust
#[derive(Clone, Copy)]
pub struct Console;

impl TtyRead for Console {
    fn read(&mut self, buf: &mut [u8]) -> usize {
        axhal::console::read_bytes(buf)
    }
}

impl TtyWrite for Console {
    fn write(&self, buf: &[u8]) {
        axhal::console::write_bytes(buf);
    }
}
```

### 4.2 tty-reader 后台任务

**InputReader 结构**（ldisc.rs:63-76）：
```rust
struct InputReader<R, W> {
    terminal: Arc<Terminal>,
    reader: R,  // Console (TtyRead)
    writer: W,  // Console (TtyWrite)
    buf_tx: CachingProd<ReadBuf>,  // rx_buf producer
    read_buf: [u8; BUF_SIZE],
    // ... 行规则处理字段
}
```

**工作流程**：
```
1. tty-reader poll() 循环
   ↓
2. reader.read(&mut read_buf) → axhal::console::read_bytes()
   ↓
3. 行规则处理（回显、信号检测）
   ↓
4. push 到 buf_tx（rx_buf）
   ↓
5. register_irq_waker(irq, waker)
   ↓
6. 返回 Pending（等待下次 IRQ）
```

### 4.3 用户 read() 调用

**调用路径**：
```
用户 read()
  → Console.read_at()
    → Terminal.read()
      → rx_buf consumer pop
        → 返回数据给用户
```

**关键发现**：tty-reader 作为后台任务持续读取 Console 数据，用户 read() 从 rx_buf 读取，**不直接读 UART 硬件**。

## 6. Console 与 AsyncUart 共享 UART 数据竞争风险

### 6.1 TX 路径数据竞争

**竞争场景**：
```
时间线:
T1: Console.write_bytes() 开始发送字节 0
  → 等待 THR_EMPTY...
T2: AsyncUart TX copier try_write() 尝试写 THR
  → THR 被 Console 持有
  → FIFO 满，LSR=0x00
T3: Console.write_bytes() 继续等待 THR_EMPTY
  → THR_EMPTY 标志不更新（UART 状态异常）
T4: TX copier retry，仍然 FIFO 满
  → 无限循环 → TX busy-loop
```

**根因**：
- Console 的同步阻塞 TX 与 AsyncUart TX copier **同时写 THR 寄存器**
- 硬件 FIFO 状态混乱（LSR=0x00）
- THR_EMPTY 标志不更新

### 6.2 IRQ Waker 冲突

**冲突场景**：
```
IRQ 10 中断到来
  → dispatch_irq(10)
    → 查找 IRQ_WAKERS[10]
      → 哪个 waker 被唤醒？
        - Console tty-reader？
        - AsyncUart RX copier？
        - AsyncUart TX copier？
```

**单一 waker 限制**：
- 当前框架每个 IRQ 只支持一个 waker
- 无法分别唤醒 RX/TX copier
- **IRQ 暴循环**：多个任务竞争唤醒

### 6.3 UART 状态不一致

**AsyncUart 重初始化风险**：
- AsyncUartDriver::new() 调用 `uart.init(config)`（async_driver.rs:52）
- **破坏 Console 已设置的 UART 状态**
- IER 寄存器被重写，可能禁用 Console 的 RX 中断

**状态查询缺失**：
- AsyncUart 未在启动时查询 UART 状态（IIR/MCR/LSR）
- 无法确认 Console 的配置是否兼容 AsyncUart

## 7. UART 状态查询方法

### 7.1 关键状态寄存器

**查询接口**（uart_16550 crate）：

| 方法 | 寄存器 | 用途 |
|------|--------|------|
| `uart.lsr()` | LSR | 查询 RX/TX FIFO 状态 |
| `uart.isr()` | ISR | 查询中断状态和类型 |
| `uart.try_receive()` | RBR | 读 RX 数据 |
| `uart.try_send()` | THR | 写 TX 数据 |

### 7.2 状态检测示例

**RX 状态检测**：
```rust
let lsr = uart.lsr();
if lsr.contains(LSR::DATA_READY) {
    // RX FIFO 有数据
    let n = uart.try_receive_bytes(&mut buf);
}
```

**TX 状态检测**：
```rust
let lsr = uart.lsr();
if lsr.contains(LSR::THR_EMPTY) {
    // TX FIFO 空，可以写数据
    let n = uart.try_send_bytes(&data);
}
```

**中断类型检测**：
```rust
let isr = uart.isr();
match isr.interrupt_type() {
    Some(InterruptType::ReceivedDataReady) => {
        // RX 中断到来
    }
    Some(InterruptType::TransmitterHoldingRegisterEmpty) => {
        // TX 空中断到来
    }
    _ => {}
}
```

## 8. 为 AsyncUart 集成的关键建议

### 8.1 避免数据竞争的策略

**方案 1：UART 硬件独占**（ADR-019 方案 D）：
- Console 和 AsyncUart **不共享 UART 硬件**
- Console 使用 axhal::console（同步阻塞）
- AsyncUart 使用独立 UART 设备（需 QEMU 多串口支持）

**方案 2：UART 状态诊断**（ADR-019 方案 A）：
- AsyncUart 启动时**查询 UART 状态**（IIR/LSR/MCR）
- 检查 Console 的配置是否兼容 AsyncUart
- 添加调试信息诊断硬件异常

**方案 3：UART 重新初始化**（ADR-019 方案 B）：
- AsyncUart 启动时**重新初始化 UART**（uart.init()）
- 风险：可能破坏 Console 的 RX 中断配置
- 需协调 Console 和 AsyncUart 的 UART 访问

### 8.2 解决 IRQ Waker 冲突

**方案：ISR + AtomicWaker**（interrupt-framework.md 4.3 节）：
```rust
static RX_WAKER: AtomicWaker = AtomicWaker::new();
static TX_WAKER: AtomicWaker = AtomicWaker::new();

fn uart_isr() {
    let isr = uart.isr();
    match isr.interrupt_type() {
        Some(InterruptType::ReceivedDataReady) => {
            uart.disable_rx_intr();  // 禁用 RX 中断
            RX_WAKER.wake();         // 唤醒 RX copier
        }
        Some(InterruptType::TransmitterHoldingRegisterEmpty) => {
            uart.disable_tx_intr();  // 禁用 TX 中断
            TX_WAKER.wake();         // 唤醒 TX copier
        }
        _ => {}
    }
}
```

**关键约束**：
- ISR 在中断上下文中执行（不能阻塞）
- `AtomicWaker::wake()` 是 ISR 安全的（无锁）
- ISR 中读 ISR 寄存器是安全的（MMIO read）

### 8.3 TX 路径设计建议

**避免 Console TX 与 AsyncUart TX copier 同时写 THR**：

**方案 1：Console TX 优先**：
- AsyncUart TX copier 启动时，**禁用 Console TX 路径**
- 所有 TX 数据通过 AsyncUart tx_buf → TX copier → UART

**方案 2：Console TX 作为 fallback**：
- AsyncUart TX copier 故障时，回退到 Console TX（同步阻塞）
- 保持调试输出能力（内核日志）
