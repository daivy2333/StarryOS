## 1. 问题陈述

用户态（Shell/benchmark）下，Async UART 的吞吐量和延迟表现**不优于甚至差于**旧的阻塞 Console UART。
异步引入的 ring buffer、copier 任务、ISR 分发等优化，在用户态的性能收益被架构开销抵消。

### 1.1 理论预期 vs 实际

| 指标 | 理论预期（Async 应更优） | 实际观察 |
|------|------------------------|---------|
| TX 吞吐量 | 更高（write 立即返回，pipeline） | 相近（受 115200 波特率限制） |
| TX 延迟 | 更低（write 不阻塞） | write() 延迟低，但端到端差异不大 |
| RX 吞吐量 | 更高（ring buffer + copier） | Kernel 内快（588 MB/s），用户态被 TTY 层瓶颈 |
| CPU 占用 | 更低（不 busy-wait） | **更高**（多任务切换 + yield storm） |
| 响应延迟 | 更低（中断驱动） | 相近（TTY ldisc 处理成为瓶颈） |

## 2. 完整的用户态 read/write 路径追踪

### 2.1 TX 路径（写）

```
User write(fd, buf, N)
  → sys_write (syscall 边界)
    → File::write() [file/fs.rs:128]
      → block_on(poll_io(self, OUT, nonblocking, || inner.write()))
        → inner.write()  (VFS → Device → Tty)
          → Tty::write_at() [tty/mod.rs:101]
            → AsyncUartWriter::write() [device_ops.rs:17]
              → DRIVER.tx.lock().push(buf)    ← 仅 push ring buffer
              → 返回 (不等待硬件)
        ← poll_io 返回 Ok(N)
  ← sys_write 返回 N
          ↓ (后台)
          TX copier 任务 [async_driver.rs:66]
            → DRIVER.tx.lock().pop()         ← pop ring buffer
            → uart_instance().lock()
            → send_bytes() → 写 UART THR
            → 部分发送 → 使能 TX 中断
            → 等待 ISR (AtomicWaker::wait)
```

**关键发现**：用户态 write() 仅 push ring buffer（~1 us），**无法反映真实串口吞吐量**。

### 2.2 RX 路径（读）

```
User read(fd, buf, N)
  → sys_read → File::read() [file/fs.rs:128]
    → block_on(poll_io(self, IN, nonblocking, || inner.read()))
      LAYER 1: Syscall/File 层等待
      
      → inner.read() → Device::read_at() → Tty::read_at() [tty/mod.rs:86]
        → block_on(poll_io(&JobControl, IN, false, || {
            ldisc.lock().read(buf)
          }))
          LAYER 2: TTY 层等待 (foreground check)

          → ldisc.read() [ldisc.rs:328]
            → block_on(poll_io(&WaitPollable, IN, false, || {
                buf_rx.pop_slice(buf)       ← 从 ldisc 内部缓冲区读
              }))
              LAYER 3: Ldisc 层等待

              ↓ 当数据到达时
              RX copier 任务 [async_driver.rs:41]
                → uart_instance().lock()
                → receive_bytes() → 读 UART FIFO
                → DRIVER.rx.lock().push()    ← push ring buffer
                → （用户进程尚未被唤醒）

              ↓ 用户 read() 路径继续
              AsyncUartReader::read() [device_ops.rs:9]
                → DRIVER.rx.lock().pop()    ← pop ring buffer
                → 返回数据给 ldisc

              ↓ ldisc InputReader.poll() 处理
                → 行规则：echo、信号检测、回显
                → push 到 buf_tx (ldisc 内部缓冲区)
                
              ← ldisc.read() 从 buf_rx pop_slice 成功
            ← LAYER 3 poll_io 返回 Ok(n)
          ← LAYER 2 poll_io 返回 Ok(n)
        ← inner.read() 返回
      ← LAYER 1 poll_io 返回 Ok(n)
  ← sys_read 返回 n
```

**关键发现**：RX 路径经过 **3 层嵌套 `block_on(poll_io(...))`**，每层都有 yield + re-schedule。

## 3. 性能瓶颈详细分析

### 3.1 瓶颈 1：Triple-nested block_on — Yield Storm

每一层 `poll_io` 的行为模式：

```rust
poll_fn(move |cx| {
    match f() {
        Ok(v) => Poll::Ready(Ok(v)),
        Err(WouldBlock) => {
            pollable.register(cx, events);  // 注册 waker
            Poll::Pending                   // 让出 CPU
        }
    }
})
```

**问题**：在 `ProcessMode::Manual` 模式下，`register` 导致**立即唤醒**：

| 层级 | Pollable | register 行为 | 效果 |
|------|----------|-------------|------|
| L1: File | → Tty → ldisc | `ldisc.register_rx_waker()` → `Manual` → `waker.wake_by_ref()` | **立即 re-schedule** |
| L2: Tty | JobControl | `JobControl::register()` → `poll_fg.register(waker)` | 正常等待（fg 不变时无唤醒） |
| L3: Ldisc | WaitPollable(None) | `WaitPollable::register()` → `waker.wake_by_ref()` | **立即 re-schedule** |

**结果**：L1 和 L3 的 waker 注册后**立即触发**，导致：
- Task yield → 立即被 re-schedule → 再次 poll → WouldBlock → yield → ...
- 形成 **yield storm**（高频 yield-re-schedule 循环）
- 每次 yield 涉及：上下文保存、调度器选择、上下文恢复
- 在无数据期间，CPU 被空转的 yield 循环消耗

**定量估计**：
- 一次 yield+reschedule 约 100-500 cycles（QEMU 中更多）
- 无数据时每秒可能数十万次 yield
- 这解释了为什么 Async 在用户态可能**反而更慢**

### 3.2 瓶颈 2：Buffer 拷贝链过长

每条数据经过的拷贝次数：

| 路径 | 拷贝链 | 拷贝次数 |
|------|--------|---------|
| **Console TX (旧)** | User buf → UART THR（逐字节） | 1 |
| **Async TX** | User buf → ring buffer → UART FIFO | 2 |
| **Console RX (旧)** | UART FIFO → ldisc buf → user buf | 2 |
| **Async RX** | UART FIFO → ring buffer → ldisc buf → user buf | **3** |

Async RX 比 Console RX **多一次 ring buffer 拷贝**（64 KB HeapRb）。

### 3.3 瓶颈 3：锁竞争

| 锁 | 竞争方 | 频率 |
|-----|--------|------|
| `DRIVER.rx.lock()` | RX copier (push) vs AsyncUartReader (pop) vs ldisc.poll_read() | 每个数据包 |
| `DRIVER.tx.lock()` | TX copier (pop) vs AsyncUartWriter (push) vs ax_println! | 每个数据包 |
| `uart_instance().lock()` | RX copier vs TX copier (交替) | 每个数据包 |
| `ldisc.lock()` | Tty::read_at (ldisc.read) vs Tty::poll (ldisc.poll_read) | 每次 read/poll |

**自旋锁代价**：在 QEMU 中，`SpinNoIrq` 和 `Mutex` 的自旋等待比真实硬件**更昂贵**（QEMU 虚拟化开销）。

### 3.4 瓶颈 4：协程调度开销

Async UART 引入的额外内核任务：

| 任务 | 栈 | 调度方式 | 唤醒频率 |
|------|-----|---------|---------|
| RX copier | ~4 KB | ISR AtomicWaker 唤醒 | 每个 RX 数据包 |
| TX copier | ~4 KB | ISR AtomicWaker + TX ring buf waker | 每个 TX 数据包 |
| （对比 Console: tty-reader 1 个任务） | | | |

每次 copier 任务唤醒 = 一次完整上下文切换（~200-1000 cycles）。

### 3.5 瓶颈 5：Manual ProcessMode 的代价

`ASYNC_TTY` 使用 `ProcessMode::Manual`：
```rust
TtyConfig {
    reader: AsyncUartReader,
    writer: AsyncUartWriter,
    process_mode: ProcessMode::Manual,
}
```

**Manual 模式特点**：
- 无独立 tty-reader 任务（节省一个任务）
- 但 `poll_read()` 在调用者的上下文中执行（同步）
- `register_rx_waker()` 直接 `wake_by_ref()` — 导致 yield storm
- ldisc 的 `read()` 方法内使用 `block_on(poll_io(...))` 阻塞等待

**对比 External 模式（旧 Console）**：
- 独立 tty-reader 任务，ISR 驱动读取
- `register_rx_waker()` 注册到 IRQ waker（不会立即唤醒）
- **不会产生 yield storm**

Manual 模式为了省一个任务，引入了 yield storm 问题。

### 3.6 硬件瓶颈：115200 波特率

串口线速度上限固定：
```
115200 bps = 11.52 KB/s （理论最大值）
```

在用户态，无论使用阻塞还是异步，**线速度都是同一上限**。这意味着：
- TX 吞吐量差异不会超过线速度限制
- 异步的优势不在原始吞吐量，而在**不阻塞调用方**（pipeline 能力）
- 用户 benchmark 测 write() 到 /dev/null 的吞吐量 → **与串口无关**，只测 VFS

## 4. 现有 Benchmark 问题

### 4.1 benchmark.c 测量的是 circle buffer 而非 UART

```
TX 吞吐量测试 [benchmark.c:44]
  → open("/dev/null", O_WRONLY)  ← /dev/null 路径，不经过 UART！
  → write(fd, buf, test_size)    ← 测的是 VFS 写入 /dev/null 速度
  → throughput = total / time     ← 这个结果是 "写入 null 设备的速度"

TX 延迟测试 [benchmark.c:127]
  → open("/dev/console", O_WRONLY)
  → write(fd, &tx, 1)            ← 测的是 push ring buffer 的时间
  → latency = end - start         ← 这个结果是 "push ring buffer 的延迟"
```

**结论**: 当前 benchmark **没有测量到实际的串口 UART 吞吐量**。TX 吞吐量测试使用的 `/dev/null` 路径完全绕过了异步串口驱动。

### 4.2 RX 测试在用户态被跳过

```c
static void test_throughput_rx(void) {
    printf("  Skipped (tested in kernel, see startup benchmark)\n");
}
```

用户态 RX 测试因为 TTY echo loop 问题（数据被 Shell 抢先读取）被跳过，改为内核态测试。但内核态测试绕过 TTY 层，直接测 ring buffer，**不能反映真实用户态 RX 性能**。

### 4.3 Kernel benchmark 无法代表用户态

`run_startup_benchmark()` [entry.rs:23] 的缺陷：
- 测试时 ISR 尚未注册（copier 刚启动可能还没有数据）
- 直接在 ring buffer 上测 push/pop，**绕过完整路径**
- 不经过 TTY/ldisc 层，不代表实际用户态性能

## 5. 对比总结: Async vs Blocking Console

| 维度 | Console (阻塞) | Async UART | 胜出方 |
|------|---------------|------------|--------|
| TX 吞吐量 | ~11.52 KB/s (线速) | ~11.52 KB/s (线速) | 持平 |
| TX 延迟 (write 返回) | 每字节 ~87 us (busy-wait) | ~1 us (push ring buf) | **Async** |
| RX 端到端延迟 | ~100 us (TTY 处理) | ~110 us (extra copy) | Console (略优) |
| CPU 占用 (TX) | 100% (发送期间) | ~1% (push) + copier 开销 | Async (usr 侧) |
| CPU 占用 (空闲等待) | 0% (无 tty-reader) | **yield storm** (Manual 模式) | **Console** |
| 代码复杂度 | 简单 (外部 crate) | 复杂 (~500 行 + ring buf) | Console |
| 内存占用 | 80 bytes ldisc buf | 128 KB ring buffer | Console |
| 上下文切换 | 无额外任务 | 2 copier 任务 + yield storm | Console |

**核心结论**: Async UART 在原始吞吐量上**不可能超过**阻塞 Console（被 115200 限制），在用户态空闲等待时因 yield storm 反而**更耗 CPU**。异步的真实优势是：
1. 写操作不阻塞调用者（pipeline 友好）
2. ISR 不会风暴（NAPI 中断合并）
3. 未来支持高性能场景（DMA、多队列）

## 6. 优化建议

### 6.1 短期：修复 yield storm

**方案 A：改为 ProcessMode::External**（推荐）
```rust
let poll_rx = Arc::new(PollSet::new());
ProcessMode::External(Box::new(move |waker| {
    poll_rx.register(waker);
}))
```
- 消除 ldisc 层 waker 立即唤醒问题
- 需要额外 tty-reader 任务（与旧 Console 相同代价）
- 但 register_rx_waker 不再做 `wake_by_ref()` → yield storm 消失

**方案 B：WaitPollable 避免立即唤醒**
```rust
impl Pollable for WaitPollable<'_> {
    fn register(&self, cx: &mut Context<'_>, _events: IoEvents) {
        // 改为使用 axhal 的 irq waker 或 schedule 机制
        // 不立即 wake_by_ref
    }
}
```

### 6.2 中期：正确 Benchmark

1. TX 吞吐量测试改为 write() 到 `/dev/console` 后调用 `tcdrain()` 等待发送完成
2. 添加 `ioctl(TIOCOUTQ)` 支持查询 TX FIFO 剩余数据量
3. 用户态 RX 测试：设置终端为 raw mode，禁用 echo，使用独立测试程序

### 6.3 长期：异步真实优势

- DMA 传输（QEMU virtio 串口）
- 多队列并发（多个 UART 设备）
- 零拷贝（VMO 直接共享）
