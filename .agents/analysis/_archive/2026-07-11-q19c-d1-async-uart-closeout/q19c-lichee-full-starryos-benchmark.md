## 1. Goal

Q19B already proved the hard UART part on Lichee RV Dock:

```text
D1 boot image -> D1 axplat -> async UART -> PLIC IRQ 18
  -> /dev/console -> user benchmark ELF -> tcdrain/FIONBIO PASS
```

The next useful target is different. It is not another embedded benchmark image; it is a board mode that behaves like the QEMU workflow:

```text
StarryOS full runtime
  -> real or packaged root filesystem
  -> load benchmark by path through load_user_app()
  -> run /bin/benchmark or shell-launched benchmark
  -> print results through /dev/console
```

The core question is therefore twofold:

1. What is still missing between the current D1 `lichee-d1-userbench` path and the normal QEMU `entry::init()` path?
2. What must be fixed in benchmark evidence before Q19C results can be compared with earlier QEMU data?

## 2. Current Paths

### 2.1 QEMU full path

CodeGraph shows the normal QEMU path in `kernel/src/entry.rs`:

```text
src/main.rs::main()
  -> starry_kernel::entry::init(args, envs)
  -> uart_init::init_uart_hardware()
  -> drivers::bench::run_startup_benchmark()
  -> pseudofs::mount_all()
  -> FS_CONTEXT.resolve(args[0])
  -> load_user_app(&mut uspace, None, args, envs)
  -> Process::new_init()
  -> ASYNC_TTY.bind_to(&proc)
  -> add_stdio() opens /dev/console
  -> spawn user task and join
```

`src/main.rs` currently passes:

```text
["/bin/sh", "-c", include_str!("init.sh")]
```

This means QEMU is not merely running a fixed ELF. It expects a root filesystem where `/bin/sh`, scripts, dynamic linker if needed, and benchmark binaries can be resolved through `FS_CONTEXT`.

### 2.2 Current D1 userbench path

The D1 userbench path is intentionally narrower:

```text
lichee_d1_init()
  -> uart_init::init_uart_hardware()
  -> bench::run_startup_benchmark()
  -> pseudofs::init_memory_root()
  -> pseudofs::mount_all()
  -> include_bytes!("../resources/benchmark.elf")
  -> load_embedded_user_app()
  -> Process::new_init()
  -> ASYNC_TTY.bind_to(&proc)
  -> add_stdio()
  -> spawn benchmark and halt
```

This path proves user mode, `/dev/console`, syscalls, TTY, `tcdrain`, and FIONBIO, but it does not prove:

- block device discovery,
- root filesystem mounting,
- path-based ELF loading from `/bin/...`,
- shell/script startup,
- swapping benchmark binaries without rebuilding the kernel.

### 2.3 Filesystem split

Current filesystem facts:

| Path | Current behavior |
|------|------------------|
| `axfs::init_filesystems(block_devs)` | Takes the first block device and initializes root FS. It panics with `No block device found!` if none exists. |
| `crates/axfs-ng/src/fs/mod.rs::new_default()` | Uses ext4 when `ext4` feature is enabled, FAT when `fat` feature is enabled. |
| `pseudofs::init_memory_root()` | D1 userbench-only escape hatch; creates a tmpfs root so devfs/proc/tmp can mount without block rootfs. |
| `pseudofs::mount_all()` | Mounts `/dev`, `/dev/shm`, `/tmp`, `/proc`, `/sys`; it assumes `FS_CONTEXT` already exists. |

The current D1 route uses `init_memory_root()` because there is no D1 block/rootfs path yet.

## 3. Gap Analysis

### 3.1 Feature gap

Current top-level features are already split cleanly:

| Feature | Meaning |
|---------|---------|
| `lichee-d1` | Smoke mode, D1 axplat + polling early output, no async UART/userland requirement |
| `lichee-d1-async-uart` | D1 async UART hardware capability with real PLIC |
| `lichee-d1-kbench` | Runtime mode: async UART + kernel benchmark then halt |
| `lichee-d1-userbench` | Runtime mode: minimal user process + embedded benchmark ELF |
| `qemu` | Full QEMU runtime: block rootfs, qemu platform, input/vsock/net/display-related assumptions |

For Q19C, do not enable `qemu` on D1. It carries QEMU PCI/virtio/display assumptions and would hide the real board gap behind unrelated constants or MMIO faults.

Recommended new runtime feature:

```text
lichee-d1-fullbench
  = lichee-d1-async-uart
  + axfeat/paging
  + axfeat/task-ext
  + dep:axfs
  + chosen D1 rootfs provider
```

Keep it separate from `lichee-d1-userbench`, because embedded benchmark remains the regression gate.

### 3.2 Rootfs provider gap

There are two viable routes.

| Route | What it proves | Cost | Recommendation |
|-------|----------------|------|----------------|
| Initramfs / packed memory root | Path-based `load_user_app()` and normal process startup without SDMMC | Low to medium | Best first Q19C gate |
| Real SDMMC/rootfs | Full board parity with QEMU disk workflow | High | Second Q19C phase |

The current memory root is empty. To emulate QEMU more closely without SDMMC, Q19C can extend this into a populated in-memory root:

```text
/bin/benchmark
/bin/sh              optional, only if shell/script parity is required
/init.sh             optional
/dev, /proc, /tmp    mounted by pseudofs::mount_all()
```

Then call `load_user_app()` with `/bin/benchmark` instead of `load_embedded_user_app()`. This moves the test from "embedded bytes bypass VFS" to "normal path lookup and cached-file ELF loading" while still avoiding SDMMC.

### 3.3 Block driver gap

For true SDMMC/rootfs parity, the missing piece is not `axfs-ng` itself. The local `axfs-ng` already supports block-backed FAT/ext4 through `AxBlockDevice`, and its D1 patch already forces `axdriver` to `block + bus-mmio` instead of PCI.

The missing piece is a D1 block device implementation and board wiring:

```text
Allwinner D1 SD/MMC controller
  -> axdriver block device
  -> AxDeviceContainer<AxBlockDevice>
  -> axfs::init_filesystems(block_devs)
  -> FS_CONTEXT root
  -> load_user_app("/bin/benchmark")
```

This should be treated as a separate hardware bring-up gate. It can fail for clock/reset/pinmux/DMA/cache reasons unrelated to UART or userland, so it should not be the first Q19C proof.

### 3.4 Loader gap

There are now two user ELF loaders:

| Loader | Source | Constraint |
|--------|--------|------------|
| `load_user_app()` | `kernel/src/mm/loader.rs` | Resolves path through `FS_CONTEXT`, handles shebang and dynamic interpreter path resolution |
| `load_embedded_user_app()` | `kernel/src/mm/loader.rs` | Reads bytes directly, bypasses rootfs, requires ET_EXEC/no relocation |

Q19C should intentionally move back toward `load_user_app()`:

1. Keep `load_embedded_user_app()` as the known-good fallback.
2. Add a fullbench mode that creates or mounts a root containing `/bin/benchmark`.
3. Call the same process setup as QEMU with `args = ["/bin/benchmark"]`.
4. Only after that passes, optionally add `/bin/sh -c init.sh`.

This isolates VFS/path loading before adding shell semantics.

### 3.5 Benchmark evidence gap

The current Q19B result is useful, but it is not yet a clean apples-to-apples continuation of the earlier QEMU benchmark series. The benchmark binary, startup chain, runtime mode, payload sizes, iteration counts, drain policy and environment are not always printed together with the results.

For Q19C planning, `benchmark.c` should be treated as part of the measurement surface, not just as a payload. The next benchmark revision should print a compact manifest before results:

```text
benchmark_version
target/mode label
startup_chain
root_provider
payload_sizes
iteration_count
drain_policy
timer_source
nonblocking_entries_tested
rx_test_mode
```

This does not require all environments to be identical. It requires that differences are visible, so the report can group data correctly instead of presenting incompatible runs as one series.

### 3.6 Board RX evidence gap

Q19B already has a nonblocking RX witness: no input returns `EAGAIN` through `open(O_NONBLOCK)` and `ioctl(FIONBIO)`. That proves part of the read-side syscall/TTY behavior, but it is not a throughput or latency measurement.

TX results cannot be used as RX performance results. The shared layers give confidence that UART initialization, PLIC integration, TTY binding and user syscall plumbing are alive, but RX still has distinct conditions:

- input source must feed the UART at a known rate,
- DATA_READY interrupts and RX copier behavior must be observed,
- FIFO overrun/backpressure is an RX-only risk,
- termios echo/raw-mode choices can change measured behavior,
- no-input `EAGAIN` is correctness evidence, not RX bandwidth evidence.

Recommended Q19C RX exploration order:

1. Keep the existing no-input `EAGAIN` checks as a regression witness.
2. Add a manual-input or host-injected fixed payload test that reads N bytes and reports bytes/time.
3. If wiring allows, add UART loopback or controlled serial injection so repeated RX measurements do not depend on human typing.
4. Only after fixed-payload RX works, discuss RX throughput/latency claims in the report.

### 3.7 64B small-packet gap

The D1 result `size=64 / iters=100 / 1.01 KB/s / 8.8% line rate` is important and should remain visible. It shows that with per-round `tcdrain`, small packets are dominated by fixed software and interrupt costs rather than physical line rate.

This is not a bad result to hide; it is the most useful clue for small-message workloads. Q19C should explore optimization strategies separately from the fullbench/rootfs work:

| Strategy | What it may improve | Risk / trade-off |
|----------|---------------------|------------------|
| Batch multiple small writes before `tcdrain` | Amortizes syscall, scheduler and drain wake overhead | Changes benchmark semantics if every message must be durable |
| Add a no-drain throughput mode | Separates write enqueue cost from physical drain cost | Must not be confused with POSIX `tcdrain` completion |
| Measure `writev` small fragments | Tests whether aggregation at syscall boundary helps | Needs clear payload accounting |
| Tune TX wake/drain path | Reduces short-packet tail latency | Must preserve TEMT correctness on real UART |
| Compare 64B/128B/256B transition | Finds break-even size for line-rate behavior | Requires identical iterations and drain policy |

These are benchmark/driver optimization questions. They should be planned in Q19C, but they should not block the first memory-root path-loader proof unless the baseline benchmark becomes unusable.

## 4. Proposed Q19C Milestones

### Q19C-M0: Benchmark evidence re-baseline

Before changing rootfs behavior, keep the existing Q19B regression gates green and make benchmark output comparable:

```text
make lichee
make lichee-kbench
make lichee-userbench
cargo check --target riscv64gc-unknown-none-elf --features lichee-d1
cargo check --target riscv64gc-unknown-none-elf --features lichee-d1-kbench
cargo check --target riscv64gc-unknown-none-elf --features lichee-d1-userbench
cargo check --target riscv64gc-unknown-none-elf --features qemu
```

Board regression gate:

```text
starry-lichee-userbench-boot.img
  -> benchmark exited with code: 0
  -> FIONBIO PASS
```

Additional exploration gates:

- benchmark output records version/mode/startup chain/root provider/iterations/payload sizes/drain policy,
- Q19B 64B result remains explicitly recorded as `size=64 / iters=100 / 1.01 KB/s / 8.8% line rate`,
- board RX has at least no-input `EAGAIN` regression plus a planned fixed-payload/manual-input or loopback test,
- report separates QEMU, embedded, memory-root, shell/script and rootfs results when parameters differ.

### Q19C-M1: Path-loaded benchmark from memory root

Goal: prove `load_user_app()` and `FS_CONTEXT.resolve("/bin/benchmark")` on D1 without SDMMC.

Implementation shape:

```text
init D1 async UART
run kernel benchmark
init populated memory root
write embedded benchmark bytes as /bin/benchmark
pseudofs::mount_all()
spawn /bin/benchmark through load_user_app()
```

Important detail: the benchmark ELF still must be ET_EXEC/no relocation if the file content is the existing embedded static ELF. The difference is delivery path, not ELF format.

Gate:

- serial log says `D1 fullbench memory-root mode`,
- `/bin/benchmark` resolves through `FS_CONTEXT`,
- user benchmark output matches Q19B sections,
- `load_embedded_user_app()` is not used in this mode.

### Q19C-M2: Shell/script parity, optional but useful

Goal: emulate QEMU's `["/bin/sh", "-c", init.sh]` model.

This requires a shell binary in the memory root or real rootfs. If the shell is dynamic, `load_user_app()` must also resolve the dynamic linker from the same rootfs. To keep scope controlled, prefer one of:

- static busybox `/bin/sh`,
- direct `/bin/benchmark` as the required gate and shell parity as optional.

Gate:

- `/bin/sh -c /init.sh` starts,
- `/init.sh` can launch benchmark,
- stdout/stderr still go through `/dev/console`.

### Q19C-M3: Real SDMMC/block rootfs discovery

Goal: replace memory root with a real block-backed root.

This is the first gate that requires a D1 SD/MMC block driver. The result must feed `AxDeviceContainer<AxBlockDevice>` into `axfs::init_filesystems()`.

Gate:

- D1 block device is discovered without enabling QEMU PCI/virtio assumptions,
- `axfs::init_filesystems()` no longer panics with `No block device found!`,
- root filesystem type is logged,
- `/bin/benchmark` can be resolved from the block root.

### Q19C-M4: Full benchmark from real rootfs

Goal: run the same benchmark workflow as QEMU, but on Lichee.

Gate:

- Android boot image remains below boot partition capacity,
- StarryOS mounts real rootfs,
- `/bin/benchmark` or `/bin/sh -c init.sh` runs,
- output has TX throughput, TX latency, FIFO boundary matrix, and nonblocking read sections,
- D1 results are recorded separately from QEMU.

## 5. Risks and Boundaries

| Risk | Why it matters | Mitigation |
|------|----------------|------------|
| Re-enabling `qemu` feature on D1 | Pulls PCI/virtio/display assumptions into a non-PCI board | Keep D1 fullbench as its own feature |
| Jumping straight to SDMMC | Expands debug surface to clock/reset/pinmux/cache/block before VFS path loading is proven | Do memory-root path-loaded benchmark first |
| Dynamic shell dependencies | `/bin/sh` may require interpreter and shared libraries | Direct `/bin/benchmark` first; shell parity second |
| Boot image size growth | D1 boot partition is about 10.1 MiB and `DWARF=y` once produced 25.6 MiB image | Keep `DWARF=n`, inspect Android boot image every time |
| Confusing Q19B and Q19C success | Embedded benchmark success does not prove rootfs or shell | Separate image names, log mode names, and result tables |

## 6. Recommended Next Action

Use the existing OpenSpec change for Q19C with three planning lanes:

1. **Q19C-0: benchmark evidence cleanup**
   - update `benchmark.c` to print a manifest,
   - plan board RX fixed-payload evidence,
   - keep 64B small-packet data visible,
   - identify small-packet latency optimization experiments.

2. **Q19C-A: memory-root fullbench**
   - new feature and make target,
   - populate `/bin/benchmark` in memory root,
   - use `load_user_app()` by path,
   - board-test benchmark output.

3. **Q19C-B: SDMMC/rootfs parity**
   - add or integrate D1 SD/MMC block path,
   - mount real rootfs through `axfs::init_filesystems()`,
   - run benchmark from real rootfs.

This keeps current progress useful: Q19B remains the UART/userland regression gate, Q19C-0 makes the evidence trustworthy, and Q19C-A proves the normal StarryOS VFS/loader startup shape before hardware block bring-up.
