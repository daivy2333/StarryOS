## 3. 关键模块详细分析

### 3.1 axdma — DMA 一致性内存（**结论：Q0~Q15 未做，Q6 重新评估**）

**arceos 实现**（`modules/axdma/src/lib.rs` + `dma.rs`）：
```rust
pub unsafe fn alloc_coherent(layout: Layout) -> AllocResult<DMAInfo>
pub struct DMAInfo {
    pub cpu_addr: NonNull<u8>,   // CPU 访问的虚拟地址
    pub bus_addr: BusAddr,       // DMA 总线地址（paddr + PHYS_BUS_OFFSET）
}
```

**核心机制**：
- 字节级 → 走 `DefaultByteAllocator`（从 `axalloc` 拉页）
- 页级 → 直接 `alloc_pages` + `update_flags(MappingFlags::UNCACHED)`
- `axmm::kernel_aspace().lock().protect()` 设置页表为 UNCACHED
- 返回 `(cpu_addr, bus_addr)` 二元组，避免混用

**NS16550 vs NS16550A 区分**（这是核心问题）：
- **NS16550（基础型号）**：**无 DMA 接口**，仅 PIO + 中断架构（FIFO + 16 字节 THR）
- **NS16550A / 16750 / 16950 等高级型号**：部分型号有自动流控，部分支持 DMA，但需要特定型号 + SoC 集成
- **JH7110 集成的是 NS16550 兼容 IP**（根据 StarryOS 配置），**SoC 是否有外部 DMA 控制器连接到 UART FIFO 是未知的**

**我们当前架构（Q0~Q15）**：
- **未做 DMA**：采用 PIO + 中断 + ring buffer + copier 模式
- **QEMU 上验证通过**：e2e 1B 134µs avg、内核态 Ring Buffer TX 456 MB/s / RX 1.1GB/s
- **QEMU 仿真限制**：不仿真串口线延迟，绝对吞吐不可信

**Q6 真板验证时的 DMA 决策点**（参考 `optimization/spec.md` O3/O40）：
- **arceos O3 明确标注**："DMA 支持 | 🟡 中 | 真板可能有 DMA 控制器"
- **arceos O40 标注**："DMA 通道配置 | 🟡 中"
- **需要验证**：
  1. JH7110 SoC 是否有 DMA 控制器
  2. DMA 控制器是否连接到 UART FIFO（不是所有 DMA 通道都能访问任意外设）
  3. DMA 传输对齐要求（PIT-005 教训：描述符需 16 字节对齐）
  4. 真板实测软件开销 vs DMA 设置开销

**可能引入 DMA 的场景**：
- 真板实测发现 PIO + 中断软件开销过高（>20% 线速）
- 需要更高波特率（230400 / 460800 bps，O41）
- 多核并发场景下中断开销成为瓶颈

**借鉴价值**：仅记录 DMAInfo 二元组模式与 UNCACHED 映射作为**通用模式参考**：
- 高吞吐网卡驱动 → **强借鉴** axdma
- 块设备驱动 → **强借鉴** axdma
- NS16550 串口 → ⏳ **Q6 决策**（O3 待办）

> ⚠️ **数据可信度声明**（Q6 阻塞）
>
> 本文档涉及的串口性能数据**全部基于 QEMU 仿真**，**未经真板实测**：

> | 数据 | 来源 | 状态 |

> - Q6 真板实测值受调度/IRQ 延迟影响，**可能低于物理定律上限**
> - **Q6 真板验证是当前唯一待办**（VisionFive2 硬件未到位）
>
> **结论**：本文档关于"NS16550 异步串口 DMA 决策"的论证**仅基于 QEMU 实测**：
> - QEMU 上 PIO + 中断软件开销已优化到低水平
> - 真板上是否同样成立，需 Q6 验证后确认
> - 若真板软件开销显著恶化，DMA 的价值评估需要重新讨论（O3/O40）

### 3.2 axasync — 异步运行时（**结论：等价已实现**）

**arceos 实现**（`modules/axasync/`）：
- `executor.rs` — Global executor（Mutex<VecDeque<Task>>）+ per-CPU local executor
- `waker.rs` — SimpleWaker（callback-based）+ timer_waker（wake_at）+ task_waker（AsyncTask）
- `time.rs` — TimerList（BinaryHeap）+ `set_oneshot_timer`
- `mmio.rs`（feature gated） — 异步 MMIO 等待

**核心特性**：
- `spawn(future)` → `JoinHandle<T>`（oneshot channel 返回结果）
- `block_on(fut)` → 自旋 executor.step() + dummy_waker
- `current_task_waker()` → 回调 `axtask::yield_now()`

**我们的等价实现**：
- `axtask::future::block_on(fut)` — 等价 `block_on`
- `embassy_sync::AtomicWaker` — 比 SimpleWaker 更标准（Rust async 生态）
- `axtask::future::timeout(fut, dur)` — 等价 `wake_at + BinaryHeap`
- ISR 中直接 `AtomicWaker::wake()` — 比 smoltcp 的 `register_recv_waker` + `Waker` 链更极简

**核心差异**：
- arceos 走**完整 async 运行时**（spawn/executor/JoinHandle），是 embassy 风格
- 我们走**轻量 async 适配**（poll_fn + AtomicWaker），是 Picol 风格
- **结果等价**，但**实现复杂度差 10x**：arceos `executor.rs` ~470 行 vs 我们 `axtask::future` 已存在

**O17 教训印证**：AtomicWaker 直接唤醒 O(1) 优于 BTreeMap 分发，arceos 走 `register_recv_waker + Waker 链` 是次优选择。

### 3.3 DwmacHal / UartPort — HAL trait 抽象（**结论：我们更精简**）

**arceos DwmacHal**（`axdriver_crates/axdriver_net/src/dwmac/mod.rs:32-54`，7 方法）：
```rust
pub trait DwmacHal: Send + Sync {
    fn dma_alloc(size: usize, align: usize) -> (PhysAddr, NonNull<u8>);
    unsafe fn dma_dealloc(paddr: PhysAddr, vaddr: NonNull<u8>, size: usize, align: usize) -> i32;
    unsafe fn mmio_phys_to_virt(paddr: PhysAddr, size: usize) -> NonNull<u8>;
    unsafe fn mmio_virt_to_phys(vaddr: NonNull<u8>, size: usize) -> PhysAddr;
    fn wait_until(duration: Duration) -> Result<(), &'static str>;
    fn configure_platform() -> Result<(), &'static str> { Ok(()) }
    fn cache_flush_range(start: NonNull<u8>, end: NonNull<u8>);
}
```

**我们 UartPort**（`uart_16550/src/async_/driver.rs:48-74`，4 方法）：
```rust
pub trait UartPort: Send + Sync + 'static {
    fn receive_bytes(&self, buf: &mut [u8]) -> usize;
    fn send_bytes(&self, buf: &[u8]) -> usize;
    fn transmitter_empty(&self) -> bool;
    fn update_ier(&self, set: IER, clear: IER);
}
```

**我们的 OS 抽象**（`uart_16550/src/os/mod.rs` + `StarryOS::drivers::os_arceos.rs`，2 trait）：
```rust
pub trait OsRuntime: Send + Sync + 'static {
    fn spawn<F: Future<...> + Send + 'static>(&self, name: &str, fut: F) -> JoinHandle<...>;
}
pub trait OsWakerSet: Send + Sync + 'static {
    fn register(&self, key: u64, waker: &Waker);
    fn wake(&self, key: u64);
}
```

**对比结论**：
- arceos DwmacHal 7 方法含 DMA + cache flush + 地址转换 — **DWMAC 复杂度所必需**（DMA ring + cache 一致性）
- 我们 UartPort 4 方法极简 — **NS16550 特性所决定**（无 DMA、无 cache flush）
- **我们 2 OS trait** vs arceos 7 HAL 方法：**总接口面 6 vs 7**，等价但**正交性更好**（OS trait 与硬件 trait 解耦）

**ADR-036 印证**：Q13 后从 5 trait 减到 2 trait（-60%），消除 dead_code；arceos 7 方法中 `mmio_phys_to_virt/mmio_virt_to_phys` 在我们用 `axmm::iomap` 直接桥接，无需 trait 抽象。

### 3.4 trust u-boot 模式（**结论：Q6 真板必备**）

**arceos ADR-004**（`openspec/specs/architecture/spec.md`）：
> arceos 启动时 U-Boot 已经初始化过 DWMAC 时钟、复位、PHY 协商。arceos 试图"重新初始化一切"会破坏 U-Boot 硬件状态，导致 PHY 链路丢失。

**arceos 反复失败**：
- 7+ 次 `failed attempt`（PIT-007 "兜兜转转回到原点"）
- commit message "revolution" + "trust u-boot" 是反思后的架构决策

**arceos 解决方案**：
1. `set_clocks_uboot()` 复用 U-Boot 已配置的时钟（不重新协商）
2. `print_preserved_status()` dump 当前状态做验证
3. 不主动 MDIO 探测 PHY
4. 仅做必要的最小补丁（如 IRQ enable）

**对我们的启示（Q6 真板验证）**：
- VisionFive2 启动时 U-Boot 已配置 PLIC、UART Clock、GPIO 复用
- 我们 QEMU 阶段可以"重新初始化一切"（QEMU 状态丢失）；真板必须 **trust u-boot**
- **预警**：`axhal/src/platform/riscv64_qemu_virt/` 当前实现可能在真板上 panic（PLIC 二次 init / UART 重新配置破坏）

**借鉴清单 B-001/B-002** 已在 P0 列出，Q6 前必须：
1. 增加 `print_preserved_status()` 验证函数
2. PLIC 改 init_primary / init_percpu 分离
3. UART init 函数检测"是否已被配置"，跳过重新初始化

### 3.5 Init Flag + Waker Future 模式（**结论：我们用 poll_fn 简化**）

**arceos smoltcp RecvFuture**（`modules/axnet/src/smoltcp_impl/future.rs:31-64`）：
```rust
pub struct RecvFuture<'a> { socket: &'a TcpSocket, buf: &'a mut [u8], init: bool }

impl Future for RecvFuture {
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<...> {
        let this = self.get_mut();
        if !this.init {                                        // ← Init Flag
            this.init = true;
            if this.socket.is_connecting() {
                return Poll::Ready(Err(AxError::WouldBlock));
            } else if !this.socket.is_connected() {
                return Poll::Ready(ax_err!(NotConnected, ...));
            }
        }
        // ... 主循环：register_recv_waker + Pending
    }
}
```

**PIT-006 教训**：AcceptFuture 遗漏了 `register_accept_waker`，永久 Pending。

**我们的等价实现**（uart_16550 reader/writer）：
```rust
// 没有 RecvFuture struct，直接 poll_fn
pub fn read(&mut self, buf: &mut [u8]) -> impl Future<Output = usize> {
    poll_fn(|cx| {
        if let Some(n) = self.try_read(buf) { return Poll::Ready(n); }
        RX_WAKER.register(cx.waker());                        // ← 必须注册
        Poll::Pending
    })
}
```

**核心差异**：
- arceos 走 `Init Flag + 显式 struct`（管理一次性初始化 + 资源借用生命周期）
- 我们走 `poll_fn + closure`（更轻量，但资源借用靠 `&mut self`）
- **不变量相同**：Pending 时必须 register waker
- **API 更简洁**：用户不需 `RecvFuture::new(socket, buf).await`，直接 `reader.read(buf).await`

**O17 教训印证**：我们 ISR 极简（read_isr + 禁中断 + wake + 返回）已蕴含 PIT-006 修复。

## 4. 不借鉴清单（明确禁忌）

### 4.1 ❓ Q6 前不引入 DMA（Q0~Q15 决策），Q6 后按需评估

**Q0~Q15 决策（基于 QEMU 实测）**：
- NS16550 自身无 DMA 接口，JH7110 是否有外部 DMA 控制器**未知**
- QEMU 上 PIO + 中断软件开销已优化到低水平
- DMA 引入对齐约束（PIT-005）+ cache flush 复杂度，QEMU 上无明显收益

**Q6 真板验证后重新评估**（参考 `optimization/spec.md` O3/O40）：
- **arceos O3**："DMA 支持 | 🟡 中 | 真板可能有 DMA 控制器"
- **arceos O40**："DMA 通道配置 | 🟡 中"
- 评估维度：
  1. JH7110 SoC 是否有 DMA 控制器
  2. DMA 控制器是否能访问 UART FIFO
  3. 真板实测 PIO + 中断软件开销 vs DMA 设置开销
  4. 是否需要更高波特率（230400 / 460800 bps，O41）

**何时重新评估**：
- Q6 真板验证后按 O3/O40 决策树走
- 若真板实测软件开销 > 20% 线速，启动 DMA 评估
- 若需要多核并发或高波特率，启动 DMA 评估
- 若 JH7110 无 DMA 通道，跳过

### 4.2 ❌ 不采用完整 async 运行时（arceos executor 模式）

**理由**：
- `axtask::future::block_on` 已满足我们的 poll_fn 风格需求
- embassy_async executor 是大依赖（executor + alloc + macros），我们已主动避免（Embassy 选型边界，L81~L84）
- `spawn()/JoinHandle` 在 unikernel 用例少（我们走 async trait 直读）

**何时重新评估**：
- 多任务并发 I/O（如网络 + 文件同时 await）
- 需要任务超时控制（当前用 `axtask::future::timeout` 替代）

### 4.3 ❌ 不引入 PHY 协商 / 时钟配置（QEMU 不需要）

**理由**：
- QEMU 仿真无真实 PHY，时钟固定
- 真板 Q6 验证时再考虑 trust u-boot 模式
- **不预先做**：避免 Karpathy 违反（不为不可能场景加抽象）

### 4.4 ❌ 不采用 register_recv_waker 多级分发

**理由**：
- O17 教训：AtomicWaker 直接 wake O(1) 优于 smoltcp register_recv_waker + Waker 链
- 中断路径必须极简（CLAUDE.md §ISR 极简原则）

## 6. 反哺上游建议

由于 arceos OPT-001 "异步 I/O 未完成"，我们的 Q0~Q15 工作是 unikernel 界**首个完整异步 UART 案例**。建议：

1. **最小反哺**：把 uart_16550 `async` feature 提交给 `arceos-org/uart_16550` 上游
2. **架构反哺**：把 "ISR 极简 + AtomicWaker + poll_fn copier" 模式写入 arceos architecture/spec.md
3. **踩坑反哺**：把 L122 (stride=4) + L140 (FIONBIO) + L168 (tcdrain) 等条目写入 arceos learned/spec.md

**风险评估**：反哺后维护负担增加（需要跟踪上游 API 变更）；建议**先稳定 Q6 真板验证 + uart_16550 v0.7 发布**，再考虑反哺。
