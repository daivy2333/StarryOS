## 1. 探究目标

Q17 的目标是把 O63 从“真板前风险记录”收敛为可实施的正确性修复清单。重点不是为 RISC-V、x86、ARM 分别写不同代码，而是确认哪些共享状态已经承担跨 hart 同步语义，并用 Rust 原子内存序表达这些语义。

本次只生成分析，不修改源码。

## 2. 当前关键路径

### 2.1 IER 更新路径

`kernel/src/drivers/uart_init.rs:81-111` 定义 `ArceOsUartPort`，其中 `update_ier()` 当前执行：

```rust
let mut val = self.ier_cache.load(Ordering::Relaxed);
val |= set.bits();
val &= !clear.bits();
self.ier_cache.store(val, Ordering::Relaxed);
self.uart.lock().set_ier(IER::from_bits_truncate(val));
```

调用来源包括 `uart_isr_wrapper()` 中的 RX/TX 禁中断回调，以及 `../uart_16550/src/async_/driver.rs` 中 RX/TX copier 重新启用中断的路径。

这不是单纯内存序问题，而是非原子 RMW 问题：两个 hart 可同时读取旧 `ier_cache`，分别修改不同 bit，最后后写覆盖先写，导致 `DATA_READY` 或 `THR_EMPTY` 使能位丢失。

### 2.2 TX completion 路径

`../uart_16550/src/async_/driver.rs:115-180` 中，`AsyncUartDriver` 暴露四阶段 drain 快照：

| 字段 | 写入方 | 读取方 | 当前内存序 |
|------|--------|--------|------------|
| `tx.is_empty()` | TX ring | `tx_completion()` | ring buffer 自己负责同步 |
| `tx_copier_active` | TX copier poll cycle | `flush()` / `tcdrain` | `Relaxed` store/load |
| `tx_staged_bytes` | TX copier pop/send | `flush()` / `tcdrain` | `Relaxed` fetch_add/fetch_sub/load |
| `transmitter_empty()` | UART MMIO | `flush()` / `tcdrain` | UART lock + MMIO 读取 |

消费方有两处：

| 消费方 | 位置 | 行为 |
|--------|------|------|
| `AsyncUartWriter::flush()` | `../uart_16550/src/async_/device_ops.rs:126-153` | poll `tx_completion()`，根据四字段决定 Ready/Pending |
| `TCSBRK / tcdrain` | `kernel/src/syscall/fs/ctl.rs:43-69` | block_on + poll `tx_completion()`，等待四阶段 drain |

`tx_copier_active` 和 `tx_staged_bytes` 不是诊断字段，它们参与 `is_drained()` 的控制流正确性。Relaxed 在单 hart QEMU 上容易通过，但在多 hart 上没有 happens-before，flush/tcdrain 可看到陈旧状态。

## 3. 风险分类

| 项 | 风险 | 原因 | 建议 |
|----|------|------|------|
| `ier_cache` | P0 | load-modify-store 在 UART 锁外，不是原子 RMW | 将 cache RMW 和 `set_ier()` 放进同一次 `self.uart.lock()` 临界区；或改成 `fetch_or`/`fetch_and` 原子 RMW |
| `tx_copier_active` | P1 | copier 发布 active/inactive，flush/tcdrain 依赖该状态 | store 用 `Release`，load 用 `Acquire` |
| `tx_staged_bytes` | P1 | copier 发布 staged byte 进度，flush/tcdrain 依赖计数 | `fetch_add`/`fetch_sub` 用 `AcqRel`，load 用 `Acquire` |
| telemetry 计数 | 非问题 | 只用于诊断统计，不决定控制流正确性 | 保持 `Relaxed` |

## 4. 是否需要按架构分叉

不需要，也不建议。

Rust 原子内存序是语言级并发契约。我们应该根据状态变量承担的同步语义选择 `Relaxed`、`Acquire`、`Release`、`AcqRel`，让编译器针对 RISC-V、x86、ARM 生成正确指令。按架构分叉会把语义藏进条件编译，增加维护成本，还容易让未来平台遗漏修复。

本项目推荐规则：

| 场景 | 内存序 |
|------|--------|
| 纯统计、纯 telemetry、不影响控制流 | `Relaxed` |
| 单 writer 发布状态，reader 依据状态继续读取或决定 Ready/Pending | store `Release` / load `Acquire` |
| RMW 计数参与同步判断 | RMW `AcqRel` / snapshot load `Acquire` |
| 多字段必须一致 | 优先锁或重新设计快照，不靠 `SeqCst` 硬凑 |
| 需要全局总顺序 | 才考虑 `SeqCst`，Q17 当前不需要 |

## 5. 推荐实施顺序

1. 先修 `ArceOsUartPort::update_ier()`，因为它是 P0，且不依赖 sibling crate 内部调整。
2. 再修 `../uart_16550/src/async_/driver.rs` 的 TX completion 原子序，保持 `flush()` 和 `tcdrain` 的四阶段语义不变。
3. 全局检查 `Ordering::Relaxed`：只处理跨 hart 且参与控制流正确性的字段，telemetry 保留。
4. 跑 StarryOS `cargo check`，再跑 QEMU benchmark，确认没有 64B write+tcdrain 退化。
5. 评估 QEMU SMP 是否能作为预检；真板到位后再做 VisionFive2 SMP stress。

## 6. 验证关注点

| Gate | 关注内容 |
|------|----------|
| 编译 | StarryOS + path 依赖 `uart_16550` 均能通过 |
| QEMU benchmark | 1B latency、64B TX、FIONBIO、tcdrain 无明显退化 |
| QEMU SMP 预检 | 如可启用多核，重点跑并发 write + flush/tcdrain |

## 8. 2026-07-03 当前分支复核

本次在 `uart-16550-lichee` 分支用 CodeGraph 复核当前源码，旧分析结论仍成立，但实施边界需要更新：

| 复核项 | 当前状态 | 对 Q17 的影响 |
|--------|----------|---------------|
| QEMU `ArceOsUartPort::update_ier()` | `kernel/src/drivers/uart_init.rs:121-126` 仍是 `ier_cache.load(Relaxed)` -> 修改 bit -> `store(Relaxed)` -> `self.uart.lock().set_ier(...)` | P0 仍需把 cache RMW 和 MMIO `set_ier()` 放进同一锁临界区 |
| D1 `ArceOsD1UartPort::update_ier()` | `kernel/src/drivers/d1_uart.rs:157-162` 也有同形态的 `ier_cache` load/store RMW，但 D1/C906 是单核平台 | 不应用 D1 真板结果证明 SMP 正确性；实施时可选择同步收敛 trait 契约，或明确 D1 因单核暂不作为 Q17 SMP 风险 |
| TX completion | `crates/uart_16550/src/async_/driver.rs:169-178` 仍对 `tx_copier_active` / `tx_staged_bytes` 使用 `Relaxed` load | P1 仍需在 `tx_completion()` 中改为 Acquire load |
| TX copier | `crates/uart_16550/src/async_/driver.rs:274-368` 仍对 active/staged 使用 Relaxed store / fetch_add / fetch_sub | P1 仍需 store Release，staged RMW AcqRel；telemetry `tx_poll` / `tx_hw_bytes` / `tx_no_progress` 继续 Relaxed |
| 影响面 | CodeGraph 显示 `update_ier` 命中 QEMU 与 D1 两个实现，`tx_completion()` 主要被 `AsyncUartWriter::flush()` 消费 | 改动前应分别评估 QEMU/D1 两条 UartPort 路径；flush/tcdrain 的 gate 以 QEMU benchmark 和后续真板复验为主 |

需要修正旧任务中的一个细节：`tx_copier_active.store(false, Relaxed)` 当前只有两处（空 ring Pending 路径和无进展 Pending 路径），另有一处 `store(true, Relaxed)`；旧 tasks.md 中“四处 store”是按旧行号/旧实现估算，实施时应以当前函数体为准。

此外，Q17 design 中关于 `kspin` / `SpinNoIrq` 的 SMP 语义应作为验证项处理：当前顶层 `smp` feature 会转发 `axfeat/smp` 和 `axplat-riscv64-visionfive2?/smp`，而 `kernel/Cargo.toml` 直接依赖 `kspin = "0.1"`。实施前应通过实际 `cargo tree -e features` 或构建输出确认 `SpinNoIrq` 在目标 SMP 配置下是否提供跨 hart 互斥；不要仅凭 QEMU 单 hart 或 D1 单核结果给出 SMP 结论。
