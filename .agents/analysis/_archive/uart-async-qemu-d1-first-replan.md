## 1. Replan Target

目标是把当前能在 QEMU 和 Lichee D1 上完成的工作前移。

现有 active roadmap 把 Q20 放在 VisionFive2 / 多 hart 验证，把 Q23 放在远期预研。这个顺序会阻塞两类当前可做工作：一是 latency / jitter / CPU 开销补测，二是用户态 ring / zero-copy / completion queue 的 UART 专用原型。

建议新的顺序如下。

| Milestone | 新目标 | 平台 | Gate |
|-----------|--------|------|------|
| Q20 | Benchmark gap closure | QEMU + D1 | 输出 latency、jitter、CPU/IRQ/copy 开销、RX fixed payload；保留 raw log |
| Q21 | User completion queue MVP | QEMU + D1 | 用户态能提交 TX 请求并读取 completion；语义不弱于 write + tcdrain |
| Q22 | User ring + zero-copy RX/TX prototype | QEMU + D1 | `mmap` ring 可用；减少一次或多次用户/内核拷贝；有 fallback |
| Q23 | Ring/completion performance decision | QEMU + D1 | 与 syscall/writev/batch-drain 对比，决定保留、收窄或回滚 |
| Q24 | Multi-hart / VisionFive2 revalidation | VF2 或等价 SMP | 复验 O63：并发 read/write、flush/tcdrain、IER enable/disable 无丢失或 hang |

这不是取消多 hart。它只是把硬件不可得或不可立即证明的 gate 放到最后。

## 3. Q20 Benchmark Gap Closure

Q20 应只做测量增强，不改驱动语义。

最小任务：

| Task | 内容 | 验证 |
|------|------|------|
| Q20.1 | 增加 jitter summary | S10/S14/S21 输出 `p99/p50`、`max/p50` |
| Q20.2 | 增加 CPU/counter summary | 输出 IRQ count、TX poll、no-progress、hw_send_zero、bytes/call |
| Q20.3 | 启用 RX fixed payload | `BENCH_RX_FIXED_BYTES > 0` 时 QEMU/D1 都有 PASS 样本 |
| Q20.4 | 保存 raw evidence | QEMU rootfs log 与 D1 serial log 分开归档 |

CPU 指标可以先用现有 telemetry 和 debug counters。`AsyncUartDriver::tx_debug_snapshot()` 已能提供 `hw_send_calls`、`hw_send_zero`、`no_progress_budget_exhausted`、`slow_poll_exhausted` 和 staged/drain 状态。

## 4. Q21 User Completion Queue MVP

Q21 应做 UART 专用 completion queue，不先追求完整 `io_uring`。

建议接口形态：

| 组件 | 作用 | 约束 |
|------|------|------|
| submit ring | 用户提交 TX/RX request descriptor | 固定大小，SPSC，先单进程 |
| completion ring | kernel 写 completion entry | 每个 entry 包含 request id、bytes、status、timestamp |
| doorbell | `ioctl` 或轻量 syscall 通知 kernel | 不在 ISR 中搬运数据 |
| wait path | poll/select 或 blocking wait | 复用现有 waker，不新增 busy loop |

MVP 只需要 TX。成功标准是用户态提交 N 个 TX request，kernel 通过 completion ring 返回完成结果，最终 `tcdrain` 语义仍由 `TxCompletion` 四阶段保证。

不建议先做通用 `io_uring`。串口只有一个设备和少量 opcode，通用化会增加 syscall、fd、权限和取消语义复杂度。

## 5. Q22 User Ring And Zero Copy

Q22 再把 Q21 的 queue 变成 `mmap` ring。

StarryOS 已有设备 mmap 框架。`DeviceOps::mmap()` 返回 `DeviceMmap`，`sys_mmap()` 已能处理 `DeviceMmap::Cache`、`ReadOnly` 和 `Physical`。这说明 UART 专用 ring 可以走现有 device mmap 路线。

推荐范围：

| 子项 | 内容 | 风险 |
|------|------|------|
| TX shared ring | 用户写 descriptor 和 payload ring，kernel copier 消费 | 必须定义所有权和 wrap 边界 |
| RX shared ring | kernel 写 RX payload，用户读 | 必须防止用户覆盖未消费数据 |
| completion ring | kernel 写 completion，用户读 | 需要 release/acquire 语义 |
| fallback | mmap 不可用时回到 write/read | 防止破坏现有 `/dev/console` |

zero-copy 的验收不能只写“少拷贝”。要列出减少了哪几次拷贝，例如 user buffer 到 kernel `IoSrc`、TTY writer 到 TX ring、RX ring 到 user buffer。

## 6. Q23 Performance Decision

Q23 是决策 gate，不是继续堆功能。

对比对象：

| 对照 | 用途 |
|------|------|
| write + tcdrain | POSIX 完成语义基线 |
| no-drain enqueue | 写入队列成本基线 |
| batch drain | 简单 batching 基线 |
| writev | 现有 syscall 聚合基线 |
| user ring + completion | 新机制 |

保留条件：

| 指标 | 要求 |
|------|------|
| correctness | 不弱于 FIONBIO、short write、tcdrain、FIFO boundary |
| latency | 1B 与 15/16/17B 不退化；P99 长尾有解释 |
| CPU | poll/send/IRQ/copy counters 不明显恶化 |
| complexity | 不影响现有 `/dev/console` 和 TTY fallback |

如果收益只来自 batch drain，保留 batch drain，不保留 ring/completion。

## 7. Q24 Multi-Hart Last

Q24 负责旧 Q20 的多 hart / VisionFive2 工作。

后置理由：

| 原因 | 说明 |
|------|------|
| QEMU/D1 已能跑当前 benchmark | 可先补测量和接口原型 |
| D1 是单 hart | 不能证明 O63，但能证明 UART 语义和性能趋势 |
| VF2 是硬件依赖 | 不应阻塞当前可验证工作 |

Q24 仍必须覆盖 O63。测试包括并发 read/write、flush/tcdrain、IER enable/disable、RX/TX waker、completion queue 在 SMP 下的 release/acquire 语义。

## 8. Proposed Optimization Spec Change

后续如果要更新 `openspec/specs/optimization/spec.md`，建议把 active milestone 表改成：

| Milestone | 目标 | 归属 |
|-----------|------|------|
| Q20 | QEMU/D1 latency+jitter+CPU/RX 补测 | O77 follow-up + benchmark gap |
| Q21 | UART user completion queue MVP | O1/O36/O54/O55 前移后的接口层 |
| Q22 | User mmap ring + zero-copy prototype | O1/O36 前移 |
| Q23 | Ring/completion 性能决策 | 新机制保留/收窄/回滚 |
| Q24 | VisionFive2 / multi-hart revalidation | O63/O64/O65/O66/O71/O38/O39 |

这样旧 Q23 的用户态 ring / zero-copy / completion queue 被前移，旧 Q20 多 hart 真板验证放到最后的硬件 gate。
