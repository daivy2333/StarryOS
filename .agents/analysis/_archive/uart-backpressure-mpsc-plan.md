# UART backpressure 与 writer 并发边界分析

> Part of StarryOS codebase analysis (branch: `uart-16550-lichee`)
> Generated by openspec-explorer at 2026-07-14
> See also: [async-uart-vs-io_uring.md](async-uart-vs-io_uring.md)

---

## 1. 探究目标

本文只分析两个近期最有价值的优化点：

1. `uart_16550` crate 应补哪些薄接口，才能让 OS 层实现 backpressure，而不把 VFS/syscall 语义搬进 crate。
2. TX ring 满时的阻塞式 backpressure / writable wait。
3. `AsyncUartWriter::Clone` 与底层 `RingBufTx` SPSC 契约不一致。

它不重新打开 Q21/Q22 的 user ring、mmap zero-copy 或 CQE 方案。当前 D1 115200 bps 已接近线速，这两个优化点的价值主要是正确性边界、可维护性和未来 SMP/multi-writer 安全，而不是当前吞吐提升。

## 2. 当前写路径

用户态写 `/dev/console` 的路径如下：

```text
sys_write/sys_writev
  -> get_file_like(fd)?.write(...)
  -> File::write()
  -> VFS node write_at()
  -> Tty::write_at()
  -> AsyncUartWriter::write()
  -> RingBufTx::push()
  -> uart-tx-copier pop_batch()
  -> UartPort::send_bytes()
```

关键事实：

| 位置 | 当前行为 |
|------|----------|
| `kernel/src/syscall/fs/io.rs` | `sys_write` / `sys_writev` 只返回底层实际写入长度 |
| `kernel/src/file/fs.rs` | `File::write()` 对普通文件路径不主动重试 partial write |
| `kernel/src/pseudofs/dev/tty/mod.rs` | `Tty::write_at()` 透传 `writer.write()` 的实际接受长度；ONLCR 映射时可把已映射字节数折回原始输入前缀 |
| `crates/uart_16550/src/async_/device_ops.rs` | `AsyncUartWriter::write()` 直接 `tx.push(buf)`，返回实际 push 字节数 |
| `crates/uart_16550/src/async_/ring_buffer.rs` | `RingBufTx::pop()` / `pop_batch()` 成功后会 `poll.wake()`，已有唤醒生产者的基础 |

结论：当前接口没有谎报“全部写完”，但阻塞 fd 缺少“等待 TX ring 有空间后继续写”的实现。调用方若忽略 short write，仍可能丢输出。

## 3. crate 薄接口边界

### 3.1 判断原则

`uart_16550` crate 应继续提供“异步 UART engine”，而不是 OS 设备文件实现。适合进入 crate 的是硬件和 ring 状态观测、waker 注册、drain snapshot；不适合进入 crate 的是 fd 阻塞/非阻塞、`poll/select/epoll` readiness、VFS `DeviceOps`、TTY line discipline 和 syscall 返回语义。

| 能力 | 是否进入 `uart_16550` | 理由 |
|------|----------------------|------|
| `RingBufTx::has_space()` / `vacant_len()` | 是 | TX ring 的通用状态观测，任何 OS poll/backpressure 都需要 |
| `RingBufRx::has_data()` / `occupied_len()` | 是 | RX readiness 的通用状态观测，可对称支持 OS poll/readable |
| `AsyncUartWriter::can_write()` | 是 | 对 ring writable 的只读封装，不引入 OS fd 语义 |
| `AsyncUartWriter::register_writable_waker()` | 是 | 暴露现有 TX ring waker，OS 自己决定如何映射到 OUT readiness |
| `AsyncUartReader::can_read()` / `register_readable_waker()` | 是 | RX 对称接口，避免 OS 直接依赖 ring 字段 |
| `TtyWrite::write_blocking()` / `WouldBlock` 错误 | 否 | 这属于 fd 阻塞/非阻塞策略，`TtyWrite::write() -> usize` 已是短写契约 |
| `Pollable` / `IoEvents` / `poll_io` | 否 | StarryOS / axpoll 专属抽象，不应污染可复用 crate |
| ONLCR、termios、job control | 否 | TTY/OS 策略，不是 UART engine |

### 3.2 推荐接口形态

建议先补最小只读/注册接口，不改变现有 `TtyRead` / `TtyWrite` trait 签名：

```rust
impl<W: OsWakerSet> RingBufTx<W> {
    pub fn vacant_len(&self) -> usize;
    pub fn has_space(&self) -> bool;
}

impl<W: OsWakerSet> RingBufRx<W> {
    pub fn occupied_len(&self) -> usize;
    pub fn has_data(&self) -> bool;
}

impl<R: OsRuntime, W: OsWakerSet, U: UartPort> AsyncUartWriter<R, W, U> {
    pub fn can_write(&self) -> bool;
    pub fn register_writable_waker(&self, waker: &Waker);
}

impl<R: OsRuntime, W: OsWakerSet, U: UartPort> AsyncUartReader<R, W, U> {
    pub fn can_read(&self) -> bool;
    pub fn register_readable_waker(&self, waker: &Waker);
}
```

这些接口让 StarryOS 可以实现 `Pollable::poll/register`，也让其他 OS 能接入自己的 reactor/等待队列。它们不承诺 blocking write、不定义 `WouldBlock`，因此仍保持 crate 通用。

### 3.3 安全注意点

`occupied_len()` / `vacant_len()` 只能作为 readiness hint，不能作为后续 push/pop 必然成功的锁定承诺。OS 层必须按“check -> register -> retry/recheck”的模式处理竞态，和现有 `flush()` 的 register-then-recheck 模式一致。

## 4. backpressure 方案

### 4.1 目标语义

建议把 UART TX 对齐 pipe/eventfd 的 `poll_io` 模式：

| fd 模式 | 期望行为 |
|---------|----------|
| 阻塞 fd | 尽量写完整个请求；ring 满时注册 OUT waker，等待 TX copier 释放空间后继续 |
| 非阻塞 fd | 已写入部分则返回 partial；完全无法写入时返回 `WouldBlock` |
| poll/select/epoll | `IoEvents::OUT` 只在 TX ring 有可用空间时置位 |

这个方案保留现有 short write 契约，但让阻塞 fd 不需要用户态忙重试。

### 4.2 推荐实现边界

最小改动应在 StarryOS TTY/VFS 层完成，不要先改 `uart_16550` 的通用 `TtyWrite` trait：

1. 先在 `uart_16550` 补齐 §3 的薄接口。
2. 在 `Tty::poll()` 中只有 TX ring 有空间时返回 `IoEvents::OUT`。
3. 在 `Tty::register()` 中对 `IoEvents::OUT` 注册 TX ring waker。
4. 在 `Tty::write_at()` 中使用 `poll_io(self, IoEvents::OUT, nb, || ...)` 包住写入循环；阻塞模式循环到请求完成或遇到错误，非阻塞模式保持 partial / `WouldBlock`。

已有 `RingBufTx::pop()` / `pop_batch()` 会在 TX copier 释放空间时 `poll.wake()`，这是实现 OUT wake 的关键基础。

### 4.3 不建议的做法

不建议让 `AsyncUartWriter::write()` 自己阻塞等待空间。原因：

- `TtyWrite::write(&self) -> usize` 是同步短写契约，没有错误返回，无法表达 `WouldBlock`。
- `embedded_io_async::Write::write(&mut self)` 可以等待，但 TTY 同步路径仍绕不过 VFS / poll 语义。
- 在 reusable `uart_16550` crate 内引入 StarryOS 的 fd 阻塞/非阻塞语义会破坏 Q13 后的 OS 抽象边界。

## 5. writer 并发边界

### 5.1 当前风险

`AsyncUartWriter` 使用 `Arc<AsyncUartDriver<...>>` 并实现 `Clone`，注释说明多个 producer 可以共享同一个 driver。但 `RingBufTx` 内部保存 `UnsafeCell<Writer<'static>>`，`push()` 的 SAFETY 前提是“只有一个 producer 写 TX buffer”。

这意味着：

- 当前单 TTY writer 路径可以成立。
- 一旦未来出现两个 task 同时持有 cloned `AsyncUartWriter` 并并发调用 `write()`，SPSC writer 侧的 `&mut Writer` 假设会被破坏。
- 仅靠 `Arc` 不能让 `RingBuffer::Writer` 变成 MPSC。

### 5.2 推荐处理顺序

不建议第一步就把 TX ring 换成 MPSC。更稳妥的顺序是：

1. **收紧契约**：删除或限制 `AsyncUartWriter::Clone`，或者把注释改成“可 clone 句柄不代表可并发 write”并在 StarryOS 只保留单 writer 所有权。
2. **加防护**：如果 API 必须保留 `Clone`，在 TX producer 侧加一个轻量互斥保护 `tx.push()`，先保证安全，再评估性能。
3. **再评估 MPSC**：只有当 Q24 SMP 或新 workload 证明多 writer 公平性/吞吐是实际需求时，才设计 MPSC ring 或多 producer 聚合层。

### 5.3 MPSC 的代价

MPSC 不是纯收益：

| 方案 | 收益 | 代价 |
|------|------|------|
| producer 侧互斥 | 改动小，保持现有 ring 和 copier | 写路径多一个锁；高并发下可能有竞争 |
| MPSC ring | 模型匹配多 writer | 新数据结构、内存序、wake、公平性和测试成本更高 |
| 单 writer 契约 | 最低成本，性能不变 | API 约束更强；未来多 writer 需要重新设计 |

当前建议优先选择“单 writer 契约 + 必要时 producer 侧互斥”，不要因为理论隐患直接重写 ring。

## 6. 建议实施计划

### Phase 0: crate 薄接口补齐

目标：在 `uart_16550` crate 中暴露 OS 集成需要的状态观测和 waker 注册能力，不引入 StarryOS 的 fd / VFS / poll 语义。

任务：

1. `RingBufTx` 增加 `vacant_len()` / `has_space()`。
2. `RingBufRx` 增加 `occupied_len()` / `has_data()`。
3. `AsyncUartWriter` 增加 `can_write()` / `register_writable_waker()`。
4. `AsyncUartReader` 增加 `can_read()` / `register_readable_waker()`。
5. 文档标明这些接口是 readiness hint，OS 层必须 register 后 recheck。

Gate：

- `uart_16550` crate host check/test/clippy 通过。
- StarryOS 现有 `/dev/console` 路径无需行为变化即可编译。
- 不新增对 `axpoll`、VFS、syscall 或 StarryOS 类型的依赖。

### Phase A: backpressure MVP

目标：阻塞 `/dev/console` 写在 TX ring 满时等待空间，非阻塞语义保持正确。

任务：

1. 基于 Phase 0 接口修改 `Tty::poll()` / `Tty::register()`，让 OUT readiness 绑定 TX ring 空间。
2. 修改 `Tty::write_at()`，用 `poll_io` 循环写完整个请求；非阻塞路径保持 partial / `WouldBlock`。
3. 增加测试或 benchmark 证据：小 TX ring 或大输出下，阻塞写不忙等、不丢前缀、`FIONBIO` 仍返回 partial / `WouldBlock`。

Gate：

- QEMU：`write()` / `writev()` / `tcdrain()` / `FIONBIO` 回归通过。
- D1：不应降低线速路径；至少复跑 Q20 中 S10/S13/S20/S40 的关键输出。

### Phase B: writer 并发契约收敛

目标：让 API 声明与 `RingBufTx` 的 SPSC 安全前提一致。

任务：

1. 搜索所有 `AsyncUartWriter::clone()` 或 `Tty<W: Clone>` 的实际使用点。
2. 若没有真实多 writer 需求，移除 `AsyncUartWriter::Clone` 或把 clone 限制留在 StarryOS TTY 构造边界。
3. 若必须保留 clone，给 `RingBufTx::push()` producer 侧加互斥，或在更高层串行化写入。
4. 增加并发写 stress：两个 task 同时写不同 byte pattern，验证不 panic、不乱序破坏单次 write 前缀、不触发数据竞争风险。

Gate：

- `uart_16550` crate async API 编译通过。
- StarryOS `/dev/console` 路径保持 Q15/Q20 关键行为。
- 若引入锁，记录 QEMU ring benchmark 和 D1 userbench 对比，确认无明显退化。

## 7. 结论

近期最值得推进的是 **crate 薄接口补齐 -> backpressure MVP**。前者让 `uart_16550` 更通用、更好集成；后者把现有 short write 契约升级为更符合阻塞 fd 预期的行为，而且复用已有 `poll_io` / `Pollable` / ring waker 模式。

`AsyncUartWriter::Clone` + SPSC 是真实安全边界问题，但当前更适合先收紧契约或加 producer 侧防护。MPSC ring 应作为有数据驱动的后续方案，而不是第一反应。
