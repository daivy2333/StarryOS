# Platform Parameter Decoupling

> Part of StarryOS codebase analysis (branch: `uart-16550-lichee`)
> Generated by openspec-explorer at 2026-06-28
> See also: [Lichee RV Dock adaptation plan](lichee-rv-dock-adaptation-plan.md), [Lichee public platform notes](lichee/public-platform-notes.md)

---

## 1. 探究目标

本次探究聚焦一个问题：当前 StarryOS 的 UART / 平台参数明显强绑定 QEMU virt，后续要同时支持 Lichee RV Dock 和 VisionFive2 时，应该如何设计更通用的参数与平台边界。

结论是：StarryOS 已经有 `MYPLAT` / `axconfig` / `axplat` 这套平台选择基础，不需要从零发明新的平台系统。但当前 async UART 初始化没有消费这套平台事实，而是在 `kernel/src/drivers/uart_init.rs` 内部写死 QEMU UART 参数。后续应引入 StarryOS 自己的轻量 platform descriptor，把“平台事实”“驱动能力”“启动策略”分层。

## 2. 当前耦合点

### 2.1 UART 初始化硬编码 QEMU

`kernel/src/drivers/uart_init.rs` 直接固定 QEMU virt 参数：

| 参数 | 当前值 | 隐含平台 |
|------|--------|----------|
| `UART_MMIO_BASE_PHYS` | `0x10000000` | QEMU virt UART |
| `UART_STRIDE` | `1` | byte-addressed NS16550 |
| `iomap` size | `0x1000` | QEMU UART MMIO range |
| raw LSR probe | `base + 5` | stride 1 register layout |
| ISR handler base | `get_uart_mmio_virt()` | 同一个 QEMU base |

这导致两个问题：

1. 换板子时不能只换构建目标，驱动内部仍会访问 QEMU 地址。
2. UART 访问模型被误认为只有 stride 差异，没有表达 MMIO access width。

Lichee RV Dock / Allwinner D1 的 console UART 是 `snps,dw-apb-uart`，base `0x02500000`，stride 4，32-bit MMIO。VisionFive2 的平台 crate 也把 UART 写成 DW APB 类设备，stride 4。二者都不能安全套用 QEMU 的 byte MMIO 假设。

### 2.2 上层 TTY 已经相对通用

上层 `/dev/console` 路径没有强绑定 QEMU：

```text
entry::init()
  -> uart_init::init_uart_hardware()
  -> ASYNC_TTY.bind_to(proc)
  -> Tty<ArceOsReader, ArceOsWriter>
  -> uart_16550 async reader/writer
```

`kernel/src/drivers/ntty_async.rs` 只依赖 `uart_init::driver()` 返回 reader/writer；`kernel/src/pseudofs/dev/tty/terminal/ldisc.rs` 通过 `TtyRead` / `TtyWrite` trait 工作。真正需要解耦的是底层 `uart_init` 如何获得平台 UART 信息，以及底层 backend 如何表达寄存器访问宽度。

### 2.3 构建系统已有平台入口

Makefile 和 `make/platform.mk` 已经支持：

| 机制 | 位置 | 作用 |
|------|------|------|
| `MYPLAT` | `make/platform.mk` | 指定目标平台 crate |
| `PLAT_CONFIG` | `make/platform.mk` | 从 platform crate 或本地文件解析 axconfig |
| `OUT_CONFIG` | `make/config.mk` | 生成 `.axconfig.toml` |
| `axconfig-gen` | `make/config.mk` / `make/build.mk` | 读取 `plat.kernel-base-paddr` 等参数 |
| `vf2` alias | `Makefile` | `APP_FEATURES=vf2 MYPLAT=axplat-riscv64-visionfive2 BUS=mmio build` |

这说明多平台支持的正确入口不是在 `uart_init.rs` 里堆 `#[cfg]` 常量，而是把平台事实接到已有 `MYPLAT` / `axconfig` 机制之后。

## 3. 上游 axplat 能提供什么

### 3.1 QEMU virt axconfig

`axplat-riscv64-qemu-virt` 的 `axconfig.toml` 已经记录：

| 字段 | 值 |
|------|----|
| platform | `riscv64-qemu-virt` |
| memory base | `0x80000000` |
| kernel base | `0x80200000` |
| PLIC base | `0x0c000000` |
| UART base | `0x10000000` |
| UART IRQ | `0x0a` |
| UART compatible | `ns16550a` 注释 |

QEMU 平台 `console.rs` 使用 `MmioSerialPort::new(UART_PADDR + PHYS_VIRT_OFFSET)`，即 byte-addressed NS16550。

### 3.2 VisionFive2 axconfig

`axplat-riscv64-visionfive2` 的 `axconfig.toml` 已经记录：

| 字段 | 值 |
|------|----|
| platform | `visionfive2` |
| memory base | `0x40000000` |
| kernel base | `0x40200000` |
| PLIC base | `0x0c000000` |
| UART base | `0x10000000` |
| UART IRQ | `0x20` |
| UART DTS 注释 | `starfive,jh7110-uart`, `snps,dw-apb-uart` |
| UART DTS 注释 | `reg-io-width = <4>`, `reg-shift = <2>` |

VisionFive2 平台 `console.rs` 使用 `MmioSerialPort::new_with_stride(..., 4)`。这表明上游 axplat 已经把“QEMU stride 1”和“真板 stride 4”区分开了，但 `uart_16550` 当前 backend 仍只做 `u8` volatile 访问。

### 3.3 axconfig 的缺口

现有 axconfig 能表达：

- memory base / size
- kernel base
- phys-virt offset
- MMIO ranges
- PLIC base
- UART base / IRQ

但不能完整表达当前 async UART 需要的所有事实：

- UART kind：NS16550、DW APB UART、SBI console 等。
- register stride：QEMU 为 1，D1 / VisionFive2 为 4。
- MMIO access width：QEMU 为 1，D1 / VisionFive2 通常应按 4 处理。
- boot image kind：QEMU 直接加载，Lichee RV Dock 是 Android boot image，VisionFive2 可能走 U-Boot image。
- early console strategy：polling UART、SBI console、axplat ConsoleIf。

因此，StarryOS 需要一个比 axconfig 更贴近本项目 UART/bring-up 需求的薄层 descriptor。

## 4. 推荐分层

### 4.1 三类信息必须分开

推荐把平台相关信息拆成三类：

| 层 | 内容 | 示例 |
|----|------|------|
| 平台事实 | 硬件地址、IRQ、内存布局 | RAM base、UART base、PLIC base、kernel base |
| 驱动能力 | 如何访问这个设备 | NS16550 byte MMIO、DW APB 32-bit MMIO、SBI console |
| 启动策略 | 镜像如何被加载 | QEMU direct、Android boot image、U-Boot image |

当前问题的根因是这三层混在一起：`uart_init.rs` 同时知道 QEMU UART base、stride、MMIO probe、ISR 注册和 async driver 启动。

### 4.2 PlatformDescriptor 草案

StarryOS 内部可以新增轻量 platform descriptor，不替代 axplat，只补足 StarryOS 自己需要的事实：

```rust
pub struct PlatformDescriptor {
    pub name: &'static str,
    pub memory: MemoryLayout,
    pub kernel: KernelImageLayout,
    pub console: ConsoleConfig,
    pub interrupt: InterruptConfig,
    pub timer: TimerConfig,
    pub boot: BootImageConfig,
}

pub struct ConsoleConfig {
    pub kind: ConsoleKind,
    pub base_paddr: usize,
    pub irq: Option<usize>,
    pub reg_stride: u8,
    pub reg_width: MmioAccessWidth,
    pub baud: u32,
}

pub enum ConsoleKind {
    Ns16550,
    DwApbUart,
    SbiConsole,
}

pub enum MmioAccessWidth {
    U8,
    U32,
}
```

不同平台给出不同实例：

| 平台 | ConsoleKind | base | irq | stride | width | boot |
|------|-------------|------|-----|--------|-------|------|
| QEMU virt | `Ns16550` | `0x10000000` | `10` | `1` | `U8` | direct QEMU |
| Lichee RV Dock | `DwApbUart` | `0x02500000` | `18` | `4` | `U32` | Android boot image |
| VisionFive2 | `DwApbUart` | `0x10000000` | `32` | `4` | `U32` | U-Boot / platform image |

这个 descriptor 可以先是 compile-time 静态常量，按 Cargo feature 或 `axconfig::PLATFORM` 选择。后续如果要解析 DTB，也应先把 DTB 解析结果落到同一个 descriptor 上，而不是让驱动到处读 DTB。

## 5. Early Console 边界

真板 bring-up 必须有一个比 async UART 更早、更小的 console：

```rust
pub trait EarlyConsole {
    fn putchar(&self, ch: u8);

    fn write_str(&self, s: &str) {
        for b in s.bytes() {
            if b == b'\n' {
                self.putchar(b'\r');
            }
            self.putchar(b);
        }
    }
}
```

推荐实现：

| 实现 | 用途 |
|------|------|
| `Ns16550U8EarlyConsole` | QEMU virt |
| `DwApbUart32EarlyConsole` | Lichee RV Dock / VisionFive2 |
| `SbiEarlyConsole` | 某些只需要最小输出的平台 |

early console 不应该依赖：

- ring buffer
- async task
- interrupt
- PLIC
- `/dev/console`
- rootfs

这样 Lichee RV Dock 第一阶段可以只验证 boot image、链接地址和 UART 访问模型，不被 async 栈和文件系统放大变量。

## 6. async UART 适配方向

### 6.1 不建议直接把 `UART_STRIDE` 改成平台配置

仅把 `UART_STRIDE` 从常量改成 `platform.console.reg_stride` 不够。原因是 `../uart_16550/src/backend/mmio.rs` 当前读写都是 `u8`：

```text
read_volatile(address.0.as_ptr()) -> u8
write_volatile(address.0.as_ptr(), value: u8)
```

D1 / VisionFive2 的 DTS 都指向 `reg-io-width = <4>`。因此需要表达 access width，不只是 stride。

### 6.2 两阶段处理

推荐拆成两个阶段：

1. StarryOS 内部先实现 `DwApbUart32EarlyConsole`，用于真板 smoke test。
2. smoke test 后再决定扩展 `uart_16550` backend，或新增 `dw_apb_uart` backend。

扩展 `uart_16550` 时应考虑：

- backend type 是否新增 `MmioAccessWidth`。
- register read/write API 是否保持 `u8` 语义，但底层用 `u32` volatile 访问低 8 位。
- ISR handler 目前接收 raw base pointer，是否也需要带 stride / access width。
- `UartPort` trait 是否继续隐藏底层访问模型，避免上层 TTY 感知硬件差异。

## 7. 建议演进路线

### M0: 文档与事实冻结

完成标准：

- Lichee RV Dock facts 已记录。
- QEMU / Lichee / VisionFive2 的 UART 差异被明确记录。
- 本文档登记到 references。

### M1: 引入 StarryOS platform descriptor

完成标准：

- 新增 `kernel/src/platform/` 或等价模块。
- QEMU descriptor 先复刻当前行为。
- `uart_init.rs` 不再直接声明 QEMU UART base。

不要求此阶段支持 Lichee 启动，只要求 QEMU 行为不变。

### M2: 拆出 early console

完成标准：

- QEMU early console 仍可输出。
- Lichee descriptor 可选择 `DwApbUart32EarlyConsole`。
- early console 不依赖 async UART。

### M3: Lichee RV Dock smoke test

完成标准：

- Android boot image 可生成。
- kernel base 使用 `0x40200000`。
- UART0 polling 输出 `[starry-d1] early boot`。

### M4: async UART 平台化

完成标准：

- async UART 初始化从 platform descriptor 读取 UART config。
- QEMU 使用 NS16550 U8 backend。
- D1 / VisionFive2 的 32-bit MMIO 路线明确：扩展 `uart_16550` 或新增 DW APB backend。

### M5: PLIC / timer / benchmark 回接

完成标准：

- PLIC IRQ 不再写死在 async UART 初始化中。
- timer 先使用 SBI，必要时接平台 timer。
- benchmark 只在 `/dev/console` 已稳定后启用。

## 8. 设计约束

1. 不把板级常量散落在 driver 内部。
2. 不让上层 TTY 知道 UART base / stride / width。
3. 不在第一阶段做运行时 DTB 泛化。
4. 不用 Lichee RV Dock 的单核结果证明 Q17 SMP 正确性。
5. 不直接修改外部 axplat crate；优先通过 `MYPLAT` / `PLAT_CONFIG` / StarryOS descriptor 衔接。
6. 不把 `axplat::console::ConsoleIf` 当作 async UART 的最终抽象。它适合 early / polling console，但 async TTY 仍需要自己的 ring buffer、waker 和 IRQ 控制。
