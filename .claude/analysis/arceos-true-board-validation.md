## 1. 目标

本文记录明扬在 arceos / VisionFive2 上做真板验证的工作方式。
重点不是 DWMAC 细节，而是可迁移到 StarryOS Q20 的验证方法。

结论：他没有把真板验证定义为“完整 OS 一次跑通”。
他把它拆成启动链、寄存器、中断、最小功能、workload 五层证据。

## 2. 启动链先可观测

VisionFive2 路线先证明镜像能被 U-Boot 加载，并能输出内核日志。
构建入口在 `scripts/make/starfive.mk:1`，产物是 FIT image `arceos.itb`。

```make
starfive: build
	gzip -9 -cvf $(OUT_BIN) > arceos-starfive.bin.gz
	mkimage -f tools/starfive/starfive_fdt.its arceos.itb
```

真板日志保存在 `modules/axasync/LOG.md`。
日志包含 OpenSBI、U-Boot、boot hart、DTB、memory region、MMIO region。
这些输出先证明启动链和串口观测成立。

这个阶段不要求网络功能通过。
它只回答三个问题：镜像是否加载、入口是否执行、串口是否可信。

## 3. 平台事实来自真板日志

明扬用日志修正了对 VisionFive2 的假设。
`modules/axasync/LOG.md` 显示 Boot HART ID 是 1，平台 HART Count 是 5。

后续分析确认 CPU0 是 S7 小核，不支持 `riscv64gc` 目标的浮点扩展。
修复在 `modules/axruntime/src/mp.rs:15`：VisionFive2 跳过 CPU0，只启动 U74 核。

```rust
if axconfig::PLATFORM == "riscv64-starfive" {
    for i in 1..=SMP {
        ...
    }
}
```

这条经验对 Q17/Q20 很关键。
多 hart 验证前必须确认 boot hart、hart 拓扑和 ISA 能力。
不能默认 hart0 是可用主核。

## 4. 先证明寄存器活着

DWMAC 初始症状是寄存器全读 `0x0`。
明扬没有先调 smoltcp 或协议栈。
他把问题降级为硬件可访问性：

| Gate | 证据 |
|------|------|
| Clock | `Clock 100` 从 `0x0` 到 `0x80000000` |
| MAC | `MAC_VERSION` 从 `0x0` 到非零 |
| DMA | `DMA_BUS_MODE` 可写后读回 |
| Init | `DWMAC device initialized successfully` |

`axdriver_crates/axdriver_net/QUICK_TEST_GUIDE.md` 把这些值写成显式检查项。
`axdriver_crates/axdriver_net/STARFIVE_DWMAC_SUCCESS_SUMMARY.md` 记录了从寄存器不可访问到可访问的过程。

这比先跑 workload 更稳。
如果寄存器全 0，benchmark 失败没有定位价值。

## 5. 对照 U-Boot，但先 dump 状态

明扬早期尝试重新初始化 clock / reset / PHY，失败很多次。
后续改成对照 U-Boot 日志，并保留对应注释。
对应实现集中在 `modules/axdriver/src/dwmac.rs:86`。

```rust
Self::set_clocks_uboot();
Self::print_preserved_status();
```

`print_preserved_status()` 在 `modules/axdriver/src/dwmac.rs:337`。
它读取 clock/reset/CPU clock 等状态，并明确说明寄存器视图不一定等于硬件可用性。

`trust u-boot` 在这里不是无条件相信。
流程是先读当前状态，再做最小改动，最后用功能验证裁决。

对 StarryOS 的边界：

| 项 | 处理 |
|----|------|
| PLIC / clock | 可借鉴 dump + preserve |
| UART FCR / IER / baud | 可重新初始化，破坏性小于 PHY |
| storage / rootfs | 不应作为 async UART 第一层 gate |

## 6. 中断拆成四个事实

明扬验证中断时拆得很细。
不是只看 ping 或 HTTP 是否成功。

| 层 | 问题 | arceos 证据 |
|----|------|-------------|
| PLIC claim | 外部中断是否到达 | `modules/axhal/src/platform/riscv64_starfive/irq.rs:101` |
| handler | handler 是否进入 | `info!("eth_irq called")` |
| device status | 设备状态是否清除 | `clear_intr_status()` |
| EOI | 是否允许下一次中断 | `PLIC.complete(...)` |

网络 handler 在 `modules/axnet/src/smoltcp_impl/mod.rs:364`。
它只打印入口、清设备状态、必要时 poll。

```rust
fn handler() {
    info!("eth_irq called");
    let rx = { ETH0.dev.lock().inner.borrow_mut().clear_intr_status() };
    if rx {
        SOCKET_SET.poll_interfaces();
    }
}
```

PLIC 路径在 `modules/axhal/src/platform/riscv64_starfive/irq.rs:101`。
顺序是 claim、dispatch、complete。

```rust
let Some(irq) = PLIC.claim(hart_ctx) else { ... };
crate::irq::dispatch_irq_common(irq.get() as usize);
PLIC.complete(hart_ctx, Irq(irq.get()));
```

明扬有一次突破是“中断可以触发多次了”。
这说明 EOI / complete 本身就是独立 gate。
后续 DMA completion 不来，又继续定位到中断 enable 位。

## 7. 功能逐层接回

明扬不是从完整网络应用开始。
他的顺序大致是：

```text
FIT image boot
  -> startup log
  -> MMIO register access
  -> clock/reset state
  -> DMA ring address/alignment
  -> TX/RX descriptor
  -> IRQ entry
  -> repeated IRQ
  -> DMA completion IRQ
  -> ping / HTTP workload
```

这条顺序的价值是排障面小。
每层失败都能回到一个具体寄存器、bit、地址或 handler。

对 StarryOS Q20，建议按类似顺序推进：

```text
VisionFive2 boot + early serial
  -> UART base/stride/access-width dump
  -> IER/IIR/LSR 原始值
  -> PLIC claim/complete
  -> RX/TX/DRAIN wake 计数
  -> kernel UART stress
  -> userbench payload
  -> full OS parity
```

完整 OS parity 应该放在后面。
它不应阻塞 Q17 多 hart UART 复验。

## 8. 对 StarryOS 的检查清单

| 阶段 | StarryOS Q20 证据 |
|------|-------------------|
| 启动链 | boot hart、DTB、memory/MMIO、first serial output |
| UART facts | base、irq、stride、access width、FIFO depth |
| 寄存器 | IER/IIR/LSR/MCR/FCR 原始值和写后读回 |
| PLIC | claim IRQ、handler entry、complete 后可重复触发 |
| async wake | RX/TX/DRAIN wake 计数和等待者状态 |
| drain | `tcdrain` 不提前返回、不 hang |
| SMP | 并发 read/write、flush/tcdrain、IER enable/disable |
| workload | kernel stress，再到 userbench |
