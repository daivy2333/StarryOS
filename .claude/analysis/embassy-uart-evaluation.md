## 摘要

本报告系统评估 embassy-rs 的 UART 驱动架构对 StarryOS 异步串口子系统的适用性。核心结论：**StarryOS 当前的自研架构（ISR → AtomicWaker → copier 任务 → ring buffer → TTY）与 embassy 的 `BufferedUart` 在架构层面同构，无根本性缺陷需要重写**。主要差异在于 ISR 职责分配（embassy 在 ISR 中直接搬运数据）和 ring buffer 实现（embassy 使用 lock-free SPSC）。具体可借鉴组件包括 `atomic_ring_buffer::RingBuffer`、`embedded_io_async` trait 体系和 tcdrain 硬件优化。

## 1. Embassy UART 生态全貌

### 1.1 三层 API 结构

embassy-stm32 提供三种 UART 抽象，覆盖不同使用场景：

| 类型 | 数据路径 | ISR 负载 | StarryOS 对应 |
|------|----------|:---:|------|
| **`Uart<'d, M>`** | 用户任务直接 `await` 单字节/缓冲区，DMA + 中断 | 中等 | —（无等价物） |
| **`BufferedUart<'d>`** | **ISR → ring buffer → AtomicWaker → 用户 read/write** | 中等 | ✅ **AsyncUartDriver + copier** |
| **`RingBufferedUartRx`** | DMA 循环模式，ISR 仅 waking | 极低 | ❌ NS16550 无 DMA |

其中 `BufferedUart` 是唯一与 StarryOS 当前架构对应的类型，也是本报告的核心对比对象。

### 1.2 核心组件清单

| 组件 | 位置 | 用途 | StarryOS 当前等价物 |
|------|------|------|------|
| `BufferedUart` | `embassy-stm32/src/usart/buffered.rs` | ISR 驱动异步串口 | `AsyncUartDriver` |
| `RingBuffer` | `embassy-hal-internal/src/atomic_ring_buffer.rs` | lock-free SPSC 环形缓冲区 | `HeapRb<u8>` + `Mutex` |
| `State` | `buffered.rs:163-187` | 静态共享状态（ring buffer + wakers） | `lazy_static!` + 独立 `static AtomicWaker` |
| `AtomicWaker` | `embassy-sync/src/waitqueue/atomic_waker.rs` | ISR 安全唤醒 | ✅ 已使用（同一 crate） |
| `embedded_io_async` traits | 社区标准 crate | 平台无关的异步 I/O trait | 自定义 `TtyRead/TtyWrite` |
| `SetConfig` trait | `embassy-embedded-hal/src/lib.rs` | 外设配置抽象 | 无 |
| `interrupt::typelevel::Binding` | embassy-stm32 宏 | 编译期中断绑定检查 | 手动 `register_irq_hook` |

**关键发现**：`embassy-embedded-hal` 是一个极小的 crate（39 行），**不提供任何 serial trait**。embassy 的串口类型通过 `embedded_io_async::Read/Write/BufRead`（社区标准 crate）暴露异步接口，而非 embassy 专属抽象。这意味着 StarryOS 可以直接 impl 这些标准 trait 而不引入 embassy 依赖。

## 2. 架构对比：ISR 极简 vs ISR 搬运

这是 StarryOS 与 embassy 之间最根本的设计分歧。

### 2.1 Embassy `BufferedUart` ISR（ISR 干重活）

ISR 直接执行 FIFO→ring buffer 的数据搬运（[`buffered.rs:34-161`](https://github.com/embassy-rs/embassy/blob/a7d1e449207c184c5a27ca9da3490b492257dfb4/embassy-stm32/src/usart/buffered.rs#L34-L161)）：

```
on_interrupt(regs, state):
  if RXNE:
    rx_writer = state.rx_buf.writer()
    while RXNE:                         // ★ 排空 FIFO
      *rx_writer.next() = DR
    if is_half_full() or eager:         // ★ 半满/eager 阈值唤醒
      state.rx_waker.wake()
  if TXE:
    tx_reader = state.tx_buf.reader()
    while TXE and tx_reader has data:
      TDR = *tx_reader.next()
      if last_byte: enable_tcie()       // ★ 最后一字节时启动 TC 中断
  if TC and tcie:
    disable_tcie()
    state.tx_done = true                // ★ 用于 flush()
    state.tx_waker.wake()
```

### 2.2 StarryOS ISR（ISR 极简）

```rust
// kernel/src/drivers/isr.rs:11-27
pub fn uart_isr_handler(_irq: usize) {
    let isr = read_isr_unlocked();
    match isr.interrupt_type() {
        Some(ReceivedDataReady) | Some(ReceptionTimeout) => {
            disable_rx_intr();    // ① 禁中断
            RX_WAKER.wake();      // ② 唤醒 copier
        }
        Some(TransmitterHoldingRegisterEmpty) => {
            disable_tx_intr();
            TX_WAKER.wake();
            if TCDRAIN_ACTIVE.load(Acquire) {
                DRAIN_WAKER.wake();
            }
        }
        _ => {}
    }
}
```

数据搬运由 copier 任务完成（`rx_copier_loop` / `tx_copier_loop`），配合 NAPI 风格的批量读取。

### 2.3 核心分歧分析

| 维度 | Embassy `BufferedUart` | StarryOS 自研 | 优劣 |
|------|----------------------|--------------|------|
| **ISR 延迟** | 取决于 FIFO 深度（STM32 v4 硬件 FIFO 可达 16 字节），~50-100 cycles/byte | 固定 ~1.5 µs（NS16550），与数据量无关 | StarryOS ISR 更可预测 |
| **任务切换次数** | 每半满唤醒一次 | 每次中断→copier 切换 1 次 | Embassy 更少 |
| **数据路径** | ISR → ring buffer → 用户任务 | ISR wake → copier → ring buffer → 用户任务 | Embassy 短一跳 |
| **ring buffer 要求** | 必须是 lock-free（ISR 可写） | 可以是 `Mutex` 保护的（仅任务上下文写） | Embassy 约束更严 |
| **代码复杂度** | 中等（ISR 更长，但省了 copier 任务） | 中等（ISR 极简，但有独立的 copier 任务逻辑） | 相当 |

**关键权衡**：embassy 的 ISR 搬运方案依赖 lock-free ring buffer（`atomic_ring_buffer::RingBuffer`）。StarryOS 当前使用 `HeapRb<u8>` + `axsync::Mutex`，这种组合**不能**在 ISR 中使用，因此 copier 任务是必要的中间层。如果 StarryOS 迁移到 lock-free ring buffer，则 ISR 直接搬运成为可行选项。

## 3. 关键机制对比

### 3.1 环形缓冲区

| 特性 | Embassy `atomic_ring_buffer::RingBuffer` | StarryOS `HeapRb<u8>` + `Mutex` |
|------|------|------|
| **并发模型** | SPSC lock-free | SPSC（`HeapRb` 本身）+ `Mutex` 外锁 |
| **ISR 安全** | ✅ 可被 ISR 直接写入 | ❌ 不能（`Mutex` 在 ISR 中不安全） |
| **分配** | `static`（`AtomicPtr<u8>` + 用户提供的 `&mut [u8]`） | `HeapRb::new(size)`（堆分配） |
| **满/空判定** | `start/end` 在 `len*2` 空间绕回 | 标准实现 |
| **内存序** | `Acquire`/`Release`（文档化了推理，[L236-260](https://github.com/embassy-rs/embassy/blob/a7d1e449207c184c5a27ca9da3490b492257dfb4/embassy-hal-internal/src/atomic_ring_buffer.rs#L236-L260)） | 依赖 `Mutex` 保证 |
| **代码量** | ~768 行（含 Reader/Writer Iterator） | 依赖外部 `ringbuf` crate |

**评估**：`atomic_ring_buffer::RingBuffer` 是 embassy 中**最值得独立借鉴的组件**。它是纯 Rust 实现，无平台依赖，有完整单元测试（[L527-768](https://github.com/embassy-rs/embassy/blob/a7d1e449207c184c5a27ca9da3490b492257dfb4/embassy-hal-internal/src/atomic_ring_buffer.rs#L527-L768)）。引入它可以消除 copier 任务中的 `Mutex` 开销，并为未来 ISR 直接搬运铺平道路。

### 3.2 AtomicWaker

StarryOS 已在使用 `embassy_sync::AtomicWaker`（v0.6.2）。该组件的核心是**无锁 2-bit 状态机**：

```
WAITING     = 0b00  // 无操作进行中
REGISTERING = 0b01  // register() 持有 waker 槽
WAKING      = 0b10  // wake() 持有 waker 槽
0b11 (REGISTERING|WAKING) = handoff  // register() 感知到 wake() 并发，代为驱动唤醒
```

`fetch_or` 原子操作（而非 `compare_exchange`）是实现 handoff 的关键 —— 它无条件发布 WAKING 位，即使 `register()` 正在执行中。RISC-V 64-bit 目标直接使用 lockless 版本。

### 3.3 TX Done / tcdrain

| 方案 | Embassy | StarryOS 当前 |
|------|---------|--------------|
| **机制** | `tcie` 硬件寄存器（Transmission Complete Interrupt） | `TCDRAIN_ACTIVE: AtomicBool`（软件标志） |
| **触发** | TX ISR 最后一字节时 `enable_tcie()` → TC 中断时 `wake` | ISR 中检查 `TCDRAIN_ACTIVE.load(Acquire)` |
| **flush() 实现** | `poll_fn { if tx_done { Ready } else { register + Pending } }` | `poll_fn { check LSR::TEMT → register DRAIN_WAKER → re-check → park }` |
| **状态管理** | 硬件自动（TC 中断自动产生） | 软件显式 set/clear |

Embassy 方案用硬件 TC 中断替代软件标志，更优雅。NS16550 同样支持 Transmission Complete 概念（`LSR::TRANSMITTER_EMPTY` bit 6），可以考虑类似优化。

### 3.4 唤醒策略

Embassy 提供三种唤醒阈值配置：

| 模式 | 触发条件 | 延迟 | StarryOS 等价 |
|------|---------|------|------|
| `eager_reads = None` | 缓冲区半满 或 IDLE line | 最多 `len/2` 字节延迟 | NAPI 中断合并 |
| `eager_reads = Some(n)` | 累积 ≥ n 字节时唤醒 | 每 n 字节一次 | 当前模式（任意数据即唤醒） |
| IDLE 检测 | 发送方停止时唤醒 | 取决于协议 | ReceptionTimeout 中断 |

StarryOS 当前通过 NAPI 阈值（16 次连续成功后切轮询）间接实现了类似效果。embassy 的半满策略更简单直接，可作为 NAPI 的简化替代。

## 4. 可借鉴与不可借鉴评估

### 4.1 可直接借鉴（低成本，高收益）

| 组件 | 收益 | 难度 | 改动范围 |
|------|------|:---:|------|
| **`atomic_ring_buffer::RingBuffer`** | 消除 `Mutex` 开销，为 ISR 搬运铺路 | 低 | `kernel/src/drivers/ring_buffer.rs` 重写 |
| **`embedded_io_async` trait impl** | 接入 Rust 嵌入式生态标准接口 | 低 | 新增 trait impl，不改核心逻辑 |
| **TC 硬件寄存器 tcdrain** | 删除 `TCDRAIN_ACTIVE: AtomicBool` 软件状态 | 低 | `isr.rs` + `ctl.rs` 修改 |
| **半满唤醒策略** | 减少高频 RX 下的唤醒次数 | 低 | `async_driver.rs` 唤醒逻辑 |

### 4.2 可借鉴但需适配（中等成本）

| 组件 | 障碍 | 建议 |
|------|------|------|
| **ISR 直接搬运** | 需要 lock-free ring buffer 就位 + ISR 延迟评估 | 先引入 `atomic_ring_buffer`，benchmark 后再决定 |
| **`interrupt::typelevel::Binding`** | 依赖 Cortex-M 中断向量表机制，与 RISC-V PLIC 不兼容 | 保留现有 `register_irq_hook` 机制 |

### 4.3 不应采用的（高成本/架构冲突）

| 组件 | 原因 |
|------|------|
| **`embassy-executor`** | 与 `axtask` 调度器冲突（已记录 L10），且替换成本极高 |
| **`embassy-stm32::BufferedUart`** | 芯片特定（STM32 PAC），移植成本 ≈ 重写 |
| **`embassy-sync` 其他同步原语**（Channel/Mutex/Watch/Semaphore） | 已验证为反优化（OE1-OE5），专用场景下性能差于当前原语 |
| **`embassy_futures::select!`** | 需要 embassy executor（OE5），与 axtask 不兼容 |
| **`InterruptExecutor`** | 让任务在中断上下文运行，直接违反 ISR 极简原则 |
| **`RingBufferedUartRx` (DMA)** | NS16550 无集成 DMA 控制器，无适配基础 |

## 5. 迁移路径建议

### 路径 A：最小借鉴（推荐）

**改动**：
1. 引入 `atomic_ring_buffer::RingBuffer`，替换 `HeapRb + Mutex`
2. 实现 `embedded_io_async::Read/Write`（trait impl 层，不改核心逻辑）
3. TC 硬件寄存器优化 tcdrain

**工作量**：1-2 周 | **风险**：低 | **收益**：消除 mutex 开销 + 标准化接口

### 路径 B：ISR 搬运重构

在路径 A 基础上：
1. ISR 直接执行 FIFO→ring buffer 搬运
2. 移除 copier 任务
3. 引入半满/IDLE 唤醒策略

**工作量**：3-4 周 | **风险**：中（ISR 变长需重新评估中断延迟） | **收益**：消除 2 个 copier 任务切换开销

### 路径 C：完全迁移到 embassy 生态

引入 `embassy-stm32`、`embassy-executor`，替换 axtask 运行时。

**工作量**：>2 个月 | **风险**：高（架构侵入 + executor 冲突） | **收益**：待评估 | **状态**：**不推荐**（已有 OE1-OE5 反模式记录 + L10 冲突记录）

## 6. 结论

1. **StarryOS 自研架构与 embassy 的 `BufferedUart` 在宏观架构上同构**（ISR → ring buffer → waker → 用户 I/O），不存在需要重写的根本性缺陷。

2. **ISR 极简原则是 StarryOS 的主动设计选择，不是缺陷**。它与 embassy 的 ISR 搬运方案各有优劣：StarryOS 的 ISR 延迟更低、更可预测；embassy 消除了额外的任务切换。对于 NS16550 的 16 字节 FIFO，ISR 延迟差异在亚微秒级别，copier 任务的开销已在 Q11 优化后被控制在合理范围内。

3. **最具价值的借鉴**是 `atomic_ring_buffer::RingBuffer`（独立 lock-free 组件，768 行纯 Rust，有完整测试），以及 `embedded_io_async` trait（标准化接口，无额外依赖）。

4. **不应引入 embassy-executor 或完整 embassy HAL**——这与 StarryOS 的 axtask 运行时冲突（L10），且 embassy 的同步原语在我们的专用场景下已被证明为反优化（OE1-OE5）。
