## 1. 结论

Q15 不应按归档的 `fix-uart-tx-completion-performance` 一次性方案整体恢复。当前两个仓库已经回滚到 pre-M4 基线并以 "start Q15 incremental re-integration" 作为新的起点：

| 仓库 | 当前 HEAD | 含义 |
|------|-----------|------|
| StarryOS | `05291f2` | rollback to pre-M4 baseline `04f8920`，开始 Q15 增量重融 |
| `uart_16550` | `95eb081` | rollback to pre-M4 baseline `60c5729`，开始 Q15 增量重融 |

推荐方案是把归档 Q15 的大包拆成 5 个可独立验证的增量，每个增量都必须能单独回滚：

1. **M0 见证层**：先扩展 benchmark 和 counters，只证明问题，不改行为。
2. **M1 性能主修复**：只融合有界 TX fast retry，解决 16B FIFO refill 的 10ms tick 台阶。
3. **M2 completion 正确性**：再融合 copier active / staged bytes / TEMT 三阶段 drain。
4. **M3 契约修复**：再改 `TtyWrite -> usize` 和 StarryOS `write_at` 短写语义。
5. **M4 所有权清理**：最后把 IER 单 owner 和 telemetry/临界区优化拆开收尾。

这个顺序的核心理由：Q15 的性能退化根因、completion 正确性、TTY 短写契约、IER 所有权是互相关联但可验证边界不同的问题。把它们重新融合成一组大提交，会再次导致性能收益、正确性修复和 API 破坏性变更无法归因。

## 2. 当前代码基线

### 2.1 StarryOS 侧

StarryOS 当前保留 OS 集成层和 TTY 接线：

| 文件 | 当前职责 | 与 Q15 的关系 |
|------|----------|---------------|
| `kernel/src/drivers/uart_init.rs` | 全局 UART 实例、`CACHED_IER`、`enable_rx_intr` / `enable_tx_intr`、ISR wrapper | 仍是外部 cached IER + callback 模型 |
| `kernel/src/drivers/os_arceos.rs` | 仅实现 `OsRuntime` / `OsWakerSet` | 已从 5 trait 收缩到 2 trait，说明回滚后边界更轻 |
| `kernel/src/pseudofs/dev/tty/mod.rs` | `Tty::write_at` 调用 writer 后总是 `Ok(buf.len())` | 短写不可见，仍是 Q15 待修 |
| `tests/benchmark.c` | 只有 64/256/1024/4096B throughput、1B latency、FIONBIO read | 缺少 Q15 要求的 1/15/16/17/31/32/33/48/49/64B FIFO 边界矩阵 |

关键现状：

```text
kernel/src/drivers/uart_init.rs:153  static CACHED_IER: AtomicU8
kernel/src/drivers/uart_init.rs:156  write_ier(value) 同时写 CACHED_IER 和 Uart16550::set_ier
```

### 2.2 `uart_16550` 侧

`uart_16550` 当前保留异步栈，但仍是 Q15 修复前的契约：

| 文件 | 当前行为 | 问题 |
|------|----------|------|
| `src/async_/driver.rs:211` | `tx_copier_loop` 每次 poll 只调用一次 `send_bytes`，未发完则 enable TX interrupt，然后 `Poll::Ready(())` | 没有有界 fast retry，也没有明确 Pending 门槛 |
| `src/async_/device_ops.rs:104` | `TtyWrite::write(&self, &[u8]) -> ()` | 调用方无法知道 TX ring 实际接收字节数 |
| `src/async_/device_ops.rs:129` | `flush()` 直接 `Ok(())` | 不等待 ring、copier staging、UART TEMT |
| `src/async_/ring_buffer.rs:179` | `RingBufTx::push` 返回实际 push 数并 wake | 底层已经具备短写信息，但 TTY trait 丢弃了它 |
| `src/async_/isr.rs:104` | ISR 接收外部 `cached_ier` 并直接 MMIO 写 IER | IER 状态仍有 driver/OS 双 owner 债务 |

`UartPort` 目前只有 `receive_bytes` / `send_bytes` 两个方法：

```text
src/async_/driver.rs:40  trait UartPort
src/async_/driver.rs:51  fn send_bytes(&self, buf: &[u8]) -> usize
```

这意味着 Q15 的 `update_ier`、TEMT 查询、completion snapshot 等能力尚未进入 crate 边界。重新融合时不要直接把所有能力一次性塞进 `UartPort`，应按增量逐步扩展，避免 trait API 一次性破坏所有适配层。

## 3. 原 Q15 归档方案的可复用部分

归档变更 `openspec/changes/archive/2026-06-21-superseded-by-q15-rollback/fix-uart-tx-completion-performance/` 的设计仍然有价值，但它更适合作为需求池，而不是直接恢复的实施计划。

| 归档决策 | 是否复用 | 新融合方式 |
|----------|----------|------------|
| D1 selective-hunk 性能见证 | 复用 | 放入 M0，先固定证据和 FIFO 边界矩阵 |
| D2 32 次有界 fast-path retry | 复用 | 放入 M1，作为唯一性能主修复 |
| D3 `tx_copier_active` / `tx_staged_bytes` | 复用 | 放入 M2，独立于 M1 验证 drain 正确性 |
| D4 TEMT 使用协作 yield | 复用但延后 | 只在 M2 ring/staging 均空后引入 |
| D5 driver 独占 IER | 复用但延后 | 放入 M4，避免与 M1/M2 混淆 |
| D6 `TtyWrite::write -> usize` | 复用但拆出 | 放入 M3，单独处理 breaking change |
| D7 metrics/wake 移出 producer 临界区 | 延后 | 放入 M4 或后续 O 项，不能混入主修复 |

## 4. 推荐增量序列

### 4.1 M0：见证层，先证明再融合

目标：建立可重复的 RED 证据，不修改生产行为。

实施范围：

| 仓库 | 文件 | 内容 |
|------|------|------|
| StarryOS | `tests/benchmark.c` | 增加 1/15/16/17/31/32/33/48/49/64/256/1024/4096B，输出 raw samples、P50/P95 |
| StarryOS | `scripts/ci-test.py` 或新增脚本 | 支持运行 benchmark 并保留机器可解析输出 |
| `uart_16550` | 测试或 feature-gated counters | 暴露 `tx_poll` / `tx_no_progress` / `tx_hw_bytes` 等 delta |

验收门槛：

- 能复现 pre-M4 与 M4 的性能差异：64B `write+tcdrain` 从约 406us 退化到约 29.99ms。
- 能在 FIFO 边界看到 16B 台阶，尤其 17/33/49/64B。
- 空闲 10 秒 counters 不持续增长，作为 busy-poll 防线。

M0 不应改 `tx_copier_loop`、`TtyWrite` 或 IER。否则后续无法区分“测试变化”与“行为变化”。

### 4.2 M1：有界 TX fast retry，唯一性能主修复

目标：消除 QEMU 快速可写路径中 16B refill 依赖 scheduler tick 的台阶，但不恢复无限 busy-poll。

建议只改 `uart_16550` 的 TX copier 相关路径：

| 文件 | 改动点 |
|------|--------|
| `src/async_/driver.rs` | 增加 `const TX_FAST_RETRY_LIMIT: usize = 32` |
| `src/async_/driver.rs:211` | `send_bytes()==0` 时最多本轮 spin retry 32 次 |
| `src/async_/driver.rs:240` | 预算耗尽时再 register TX waker / enable THRE / final recheck / Pending |

当前 `tx_copier_loop` 的一个风险是 poll 闭包总是 `Poll::Ready(())`，它依赖外层 `loop` 重新 poll。M1 应把“可快速继续”和“必须等待 IRQ”表达清楚：

```text
ring 有数据
  -> send_bytes > 0: cursor 前进，继续当前 poll
  -> send_bytes == 0:
       retry <= 32 且恢复可写: 继续当前 poll
       retry 用尽: register TX_WAKER -> enable THRE -> final recheck
           -> 可写: 继续
           -> 不可写: Poll::Pending
```

不得做的事：

- 不改 `TtyWrite` 返回值。
- 不实现三阶段 drain。
- 不移动 IER 所有权。
- 不扩大 32 次预算来追性能。

验收门槛：

- 64B-4096B Async `write+tcdrain` 不劣于同环境阻塞基线 10%。
- 1/15/16/17/31/32/33/48/49/64B 不再出现 10ms/refill 台阶。
- 空闲 10 秒 `tx_poll` / `tx_no_progress` 不持续增长。

### 4.3 M2：三阶段 completion 与 `flush` / `tcdrain`

目标：修复“写入 ring 之后不代表硬件已发送完成”的正确性问题。

需要新增的 driver 状态：

| 状态 | 写入者 | 读取者 | 用途 |
|------|--------|--------|------|
| `tx_copier_active` | TX copier | flush/tcdrain | 区分 ring 已空但 copier 正在处理 |
| `tx_staged_bytes` | TX copier | flush/tcdrain | 表示已 pop 但未完全提交到 UART 的 bytes |
| TEMT snapshot | UartPort | flush/tcdrain | 判断 shift register 是否真正空 |

建议接口不要一次性暴露底层寄存器，而是给 `AsyncUartDriver` 提供 completion snapshot：

```text
TxCompletion {
  ring_empty: bool,
  copier_active: bool,
  staged_bytes: usize,
  transmitter_empty: bool,
}
```

StarryOS 侧的 `TCSBRK` / `tcdrain` 应复用 driver completion，而不是继续用 ring empty 或旧 `DRAIN_WAKER` 推断。当前 `embedded_io_async::Write::flush` 直接 `Ok(())`，M2 后必须等待：

```text
ring queued == 0
AND copier_active == false
AND staged_bytes == 0
AND UART TEMT == true
```

TEMT 等待不要依赖独立 IRQ。归档方案里的协作 yield 仍然合理，但应只在 ring/staging 都空后启用，避免形成 drain storm。

### 4.4 M3：TTY 短写契约

目标：让 backpressure 对 VFS 可见。

当前底层 `RingBufTx::push` 已返回实际接收字节数，但 `TtyWrite::write` 和 StarryOS `Tty::write_at` 丢弃了结果：

```text
uart_16550/src/async_/device_ops.rs:104  fn write(&self, buf: &[u8]) { self.driver.tx.push(buf); }
StarryOS/kernel/src/pseudofs/dev/tty/mod.rs:105  write_at() -> Ok(buf.len())
```

推荐改动：

| 层 | 新契约 |
|----|--------|
| `uart_16550::tty::TtyWrite` | `fn write(&self, buf: &[u8]) -> usize` |
| `AsyncUartWriter` | 返回 `RingBufTx::push` 的实际值 |
| PTY writer | 返回 `push_slice` 的实际值，保留 wake |
| StarryOS `Tty::write_at` | 返回实际写入量；满 ring 时交给 blocking/nonblocking 层等待或返回 WouldBlock |
| ldisc echo | 明确 best-effort，忽略短写但不能假装完整写入给用户路径 |

M3 是 breaking change，必须在 M1/M2 之后做。原因是它可能改变用户态 write 行为和阻塞逻辑，混入 M1 会污染性能归因。

### 4.5 M4：IER 单 owner 与次要优化

目标：清除长期架构债务，但不影响 M1-M3 的性能/正确性判断。

当前 IER 状态由 StarryOS `CACHED_IER` 和 `uart_16550` ISR 共同操作：

```text
StarryOS write_ier -> Uart16550::set_ier
uart_16550::isr::disable_tx_intr -> cached_ier + direct MMIO write
tx_copier_loop -> enable_tx_intr callback -> StarryOS write_ier
```

重新融合时应把 IER owner 收回 `UartPort` 或更明确的 port-control trait：

```text
trait UartPort {
  fn receive_bytes(&self, ...)
  fn send_bytes(&self, ...)
  fn update_ier(&self, set: IER, clear: IER)
  fn transmitter_empty(&self) -> bool
}
```

但这一步必须等 M1/M2/M3 都有证据后再做。它会同时触及 ISR、copier、StarryOS adapter 和 MMIO 锁边界，风险高于 M1 的局部 retry。

metrics/wake 移出 producer 临界区也应作为 M4 或后续优化项单独 A/B，不能和功能修复同提交。

## 5. 依赖关系与阻塞点

推荐依赖图：

```text
M0 benchmark/counters
  -> M1 bounded fast retry
      -> M2 completion/flush/tcdrain
          -> M3 TtyWrite short-write contract
              -> M4 IER single owner + telemetry/critical-section optimization
```

可以并行准备但不能并行合并的工作：

| 可提前准备 | 合并约束 |
|------------|----------|
| M3 的 callers 清单和编译修复草稿 | 必须等 M1/M2 通过后合并 |
| M4 的 `UartPort` trait 草案 | 必须等 M2 确定 TEMT/completion API 后合并 |
| benchmark 脚本输出格式 | 可作为 M0 直接合并 |
| telemetry feature gate 草案 | 不得影响 M1 counters 语义 |

## 6. 验证矩阵

每个增量的最小验证集：

| 增量 | 必跑验证 | 失败时处理 |
|------|----------|------------|
| M0 | benchmark 编译运行；输出含 FIFO 边界尺寸、raw/P50/P95、commit/tick/FIFO | 修测试，不改 driver |
| M1 | `uart_16550` async tests；StarryOS QEMU benchmark；idle 10 秒 counter | 回滚 M1，不扩大 retry 上限 |
| M2 | flush/tcdrain race tests；QEMU 1B/64B/4KiB `write+tcdrain` | 修 completion，不改 M1 retry |
| M3 | StarryOS TTY/PTY/echo callers；blocking/nonblocking write 行为 | 修 VFS 等待语义，不改 driver 性能 |
| M4 | IER 交错测试；Shell boot；IRQ storm / lost interrupt 观测 | 回滚 M4，保留 M1-M3 |

发布前仍需 VisionFive2 或等价真板数据。QEMU 只能证明 scheduler tick 量化回归和 FIFO 边界行为，不能替代慢硬件上的 MMIO retry 成本验证。

## 7. 关键风险

| 风险 | 触发点 | 缓解 |
|------|--------|------|
| 32 次 retry 在真板上浪费 MMIO 读 | M1 | 固定上限、记录 no-progress/CPU，失败回滚而不是扩大预算 |
| completion 状态内存序错误导致 `tcdrain` 提前返回 | M2 | active/staged Release 写，drain Acquire 读，check-register-recheck |
| `TtyWrite -> usize` 破坏 PTY/echo | M3 | 用 CodeGraph callers 全迁移，echo 标注 best-effort |
| IER 单 owner 改动引入丢中断 | M4 | 专门做 enable/disable 交错测试，保持 ISR 极简 |
| benchmark 输出不足以归因 | M0 | 所有结果必须包含 commit、tick、FIFO、QEMU/board、blocking baseline |

## 9. 最小下一步

最小可执行下一步是只做 M0：

1. 扩展 `tests/benchmark.c` 的尺寸矩阵到 `1/15/16/17/31/32/33/48/49/64/256/1024/4096B`。
2. 输出 raw samples、P50/P95、每轮 commit/tick/FIFO/QEMU 信息。
3. 在不改 driver 的情况下跑当前 HEAD，建立 Q15 重新融合的 RED 基线。

M0 通过后再进入 M1。不要从 M2/M3/M4 开始，因为这些增量无法单独解释 q15 的性能退化是否被修复。
