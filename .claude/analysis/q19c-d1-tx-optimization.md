## 1. 问题陈述

Q19C.8d 已修复 D1 `send_bytes()` 16B FIFO burst 和 TTY OPOST/ONLCR short-write 计数，S11 1024B 正确发送恢复。但真板 `docs/NewDate.md` 的 gated TX debug snapshot 显示三个剩余症状：

### 症状 1: `hw_send_zero` 高（97% send_bytes 调用返回 0）

S11 TX enqueue（no-drain，final drain）真板数据：

| size | hw_send_calls | hw_send_zero | zero 比例 | no_progress_budget | 成功次数 |
|------|---------------|--------------|-----------|--------------------|---------|
| 64   | 13,966        | 13,566       | **97.1%** | 399                | 400 (6400/16) |
| 256  | 55,966        | 54,366       | 97.1%     | 1,599              | 1,600 |
| 1024 | 143,361       | 139,264      | 97.1%     | 4,096              | 4,096 |

**规律**：每发 16 字节（一个 FIFO），平均要调用 `send_bytes()` 约 35 次，其中 34 次返回 0。

### 症状 2: `no_progress_budget_exhausted` 频繁

`TX_FAST_RETRY_LIMIT=32`，每次 FIFO full 时 32 次 busy spin 全部失败 → budget exhausted +1 → 等 ISR wake。

- size=64: 399 次 budget exhausted（400 次 FIFO fill，最后一次不需要等）
- size=1024: 4096 次 budget exhausted

**数学关系**：`no_progress_budget ≈ hw_send_bytes / 16`，每次 FIFO fill 都要经历一次 budget exhausted。

### 症状 3: P99 长尾

S10 drain-each（真板 100 次迭代）：

| size | P50 | P95 | P99 | P99/P50 | max_line_ratio |
|------|-----|-----|-----|---------|----------------|
| 64   | 5.610ms | 5.612ms | 5.621ms | 1.00x | 1.04 |
| 256  | 21.999ms | 22.001ms | **50.872ms** | 2.31x | 2.34 |
| 1024 | 87.558ms | 87.587ms | **117.447ms** | 1.34x | 1.35 |

S21 FIFO boundary matrix 更明显：

| size | P99 | 跳变点 |
|------|-----|--------|
| 1    | 0.231ms | 基线 |
| 15   | **14.843ms** | **跨 FIFO 边界 P99 暴涨 64x** |
| 16   | 15.204ms | |
| 49   | 18.022ms | |

**关键观察**：size=1 的 P99 只有 0.23ms；只要超过 1 字节，P99 就跳到 14ms+。说明 P99 长尾的根源是**等 FIFO 排空 + 等 THRE ISR wake**。

## 2. TX Copier 算法分析

源码位置：`crates/uart_16550/src/async_/driver.rs:418-579`（`tx_copier_loop`）

### 2.1 算法流程

```
tx_copier_loop:
  loop {
    poll_fn(|cx| {
      1. 若 staged 数据发完，从 ring pop 一批新数据 (≤1024B 到 write_buf)
         - 若 ring 空：
           - 若 transmitter_empty() → wake DRAIN_WAKER
           - 否则：注册 TX_WAKER + update_ier(THR_EMPTY) + 再查 TEMT
           - 注册 ring waker → Poll::Pending

      2. Bounded retry 内循环：
         loop {
           sent = send_bytes(write_buf[cursor..])
           - sent > 0 → 重置 retries=0，cursor += sent，continue
           - sent == 0 → retries++
             - retries ≤ 32 → continue (busy spin_loop hint)
             - retries > 32 → no_progress_budget_exhausted++
               - 注册 TX_WAKER + update_ier(THR_EMPTY)
               - final recheck: 再调一次 send_bytes
               - 仍 0 → Poll::Pending 等 ISR
         }

      3. 全发完 → TEMT poll 256 次 → 注册 TX_WAKER
         - 若 transmitter_empty → wake DRAIN_WAKER
         - 否则 → update_ier(THR_EMPTY)
    }).await
  }
```

### 2.2 关键常量

| 常量 | 值 | 位置 | 用途 |
|------|-----|------|------|
| `TX_FAST_RETRY_LIMIT` | 32 | `driver.rs:33` | FIFO full 时 busy spin 上限 |
| `TX_TEMT_POLL_LIMIT` | 256 | `driver.rs:35` | 发完后等 TEMT 的 poll 上限 |
| `COPIER_BUF_SIZE` | 1024 | `driver.rs:31` | 单次 ring pop batch 缓冲 |
| `NAPI_THRESHOLD` | 16 | `driver.rs:27` | RX NAPI polling 阈值（与 TX 无关） |

### 2.3 D1 `send_bytes()` 实现

源码位置：`kernel/src/drivers/d1_uart.rs:142-157`

```rust
fn send_bytes(&self, buf: &[u8]) -> usize {
    if buf.is_empty() { return 0; }
    let lsr = self.read_reg(UART_LSR);
    if lsr & LSR_THRE == 0 { return 0; }  // FIFO 不空 / 未就绪
    let len = buf.len().min(TX_FIFO_SIZE);  // TX_FIFO_SIZE = 16
    for &byte in &buf[..len] {
        self.write_reg(UART_RBR_THR, byte as u32);
    }
    len
}
```

**关键点**：D1 `send_bytes()` 是纯同步、无 retry 的。THRE 置位时填 16B，否则立即返回 0。所有 retry 逻辑都在 `tx_copier_loop` 侧。

## 3. 根因分析

### 根因 1: 32 次 busy spin 在 D1 上完全无效

**数学**：
- D1 UART @115200bps，16B FIFO 排空需要 `16 × 8 / 115200 = 1.11ms`
- 32 次 `core::hint::spin_loop()` 在**亚微秒级**就跑完（C906 流水线 + 分支预测）
- 所以 32 次重试期间 FIFO 仍然是满的，全部返回 0

**推论**：
- 必然走到 budget exhausted → 等 ISR
- `hw_send_zero = 32 × (FIFO fill 次数) + final_recheck_zero` 就是这个数学关系
- 真板数据 `no_progress_budget ≈ hw_send_bytes / 16` 完美吻合

**QEMU 差异**：QEMU 的 NS16550 模型在 THR 写完后几乎立即重新置位 THRE（不模拟真实 1.11ms 排空延迟），所以 QEMU 上 32 次 spin 期间就能等到 THRE，budget exhausted 几乎不发生。这掩盖了 D1 上的问题。

### 根因 2: D1 THRE IRQ 边沿丢失（L255 已记录）

**症状**：PLIC 进入 UART IRQ 18 但 IIR=`0xc1`（bit0=1 no pending），有效 THRE 只偶发 `0xc2`。

**根因推测**：
- DW APB UART 的 THRE IRQ 是边沿触发，要求 IER THR_EMPTY 从 disable→enable 转换时 LSR THRE 已置位
- D1 PLIC 电平触发模式 + UART IIR 清除逻辑可能导致 race：IRQ 拉低 → PLIC 看到 → CPU 进入 ISR → 读 IIR 时 UART 已清 pending → IIR=0xc1
- QEMU 不模拟这个 race（NS16550 模型简化）

**影响**：
- budget exhausted 后 copier 等 TX_WAKER wake，但 ISR 可能延迟或丢失
- 偶尔的延迟 wake 就是 P99 长尾的直接来源
- S21 size=1 → size=15 的 P99 跳变 64x 证明：只要需要等 FIFO 排空，就暴露 THRE ISR 不可靠

### 根因 3: P99 跳变点 = FIFO 排空等待

**关键数据点**：
- size=1: 不需要等 FIFO 排空（THR 直接写 1 字节），P99=0.23ms
- size=15: 必须等 16B FIFO 排空才能写下一次 → 等 THRE ISR
- P99=14-18ms ≈ FIFO 排空时间（1.11ms）× 调度/ISR 抖动倍数（~13x）

**为什么 P99 不是 P50 的 1.x 倍而是 2-3 倍**：
- P50 路径：budget exhausted → 等 ISR → ISR 正常到达 → wake → 继续
- P99 路径：budget exhausted → 等 ISR → ISR 延迟/丢失 → 某种 fallback 才能继续
- 当前唯一的 fallback 是：下一次 ring 有新数据时 copier 被再次 poll，或 DRAIN_WAKER 在 TEMT 时 wake
- 这两个 fallback 都不确定时间，所以 P99 长尾可达 50ms+

## 4. 已证伪方案：`TX_FAST_RETRY_LIMIT=0` + drain 注册 `TX_WAKER`

### 4.1 尝试的方案

- `TX_FAST_RETRY_LIMIT=0` → `send_bytes` 返回 0 后立即 await，不 spin
- drain 路径（`flush()` / `tcdrain`）也注册 `TX_WAKER`，不只依赖 `DRAIN_WAKER`

### 4.2 失败症状

benchmark 进程 spawned 后卡死，没有任何 benchmark section 输出。

### 4.3 失败根因

1. `=0` 意味着**完全依赖 THRE ISR 唤醒**才能前进
2. D1 THRE ISR 有边沿丢失（根因 2）
3. 第一次 16B FIFO 填满后，ISR 不来 → copier 永远 Pending
4. drain 注册 TX_WAKER 也救不了——因为 TX_WAKER 同样由 THRE ISR 唤醒
5. → 第一次 stdout write 就死锁

### 4.4 结论（已写入 L266）

D1 THRE 唤醒路径还不能作为唯一进展来源。必须保留软件前进 fallback 或 bounded polling。此方案**不得作为默认修复**。

## 6. 优化方向

### 方向 A: 时间预算替代计数预算

**思路**：将 `TX_FAST_RETRY_LIMIT` 从 32 次计数改为时间预算（如 500µs-1ms）。

**实现草图**：
```rust
// 替代 retries 计数
let deadline = Instant::now() + Duration::from_micros(500);
loop {
    let sent = self.uart.send_bytes(...);
    if sent > 0 { break; }
    if Instant::now() >= deadline {
        // budget exhausted
        break;
    }
    core::hint::spin_loop();
}
```

**预期收益**：
- 115200bps 16B 排空 1.11ms，500µs 预算能覆盖部分排空
- 实际上 500µs 内 FIFO 仍在排空中，`send_bytes` 仍返回 0
- **但**：1ms 预算能覆盖整个 FIFO 排空周期，可能减少 budget exhausted 事件
- 收益取决于预算值选择

**风险**：
- 低 — 时间预算比计数更自适应
- QEMU 不受影响（QEMU THRE 立即响应，预算内就能成功）
- 需要确认 `Instant::now()` 在 no_std 内核环境可用（`axhal` 提供）

**注意**：时间预算**单独不能解决 P99 长尾**，因为预算耗尽后仍要等 ISR。需配合方向 B/E。

### 方向 B: 软件 LSR poll watchdog

**思路**：budget exhausted 后，除了注册 TX_WAKER，再加一个 bounded 周期 LSR poll fallback。

**实现草图**：
```rust
// budget exhausted 后
TX_WAKER.register(cx.waker());
self.uart.update_ier(IER::THR_EMPTY, IER::empty());

// 新增：启动 watchdog
loop {
    // 短 spin 后 yield
    for _ in 0..4 {
        if self.uart.thre_ready() { break; }
        core::hint::spin_loop();
    }
    if self.uart.thre_ready() {
        // 软件补唤醒：THRE 已就绪但 ISR 没来
        break;  // 退出 await，回到内循环
    }
    // yield 让出调度
    yield_now().await;
}
```

**预期收益**：
- 即使 THRE ISR 丢失，watchdog 也能检测 THRE 重新置位并 wake
- 直接破解 P99 长尾（最坏情况 = watchdog 周期，而非 ISR 永远不来）
- 同时减少 `hw_send_zero`（watchdog 检测到 THRE 后立即恢复发送）

**风险**：
- 低-中 — 需要调度机制（`yield_now` 或 `task::yield_now`）
- 只在 budget exhausted 路径生效，不影响 fast path
- 需要确认不会与 TX_WAKER 重复唤醒造成 race

**D1 特化**：这个方向本质是针对 D1 THRE 边沿丢失的软件 workaround。

### 方向 C: 指数退避 spin

**思路**：32 次 spin 改为：前 N 次 `spin_loop`，中间 `yield_task`，后期短 `sleep`。

**预期收益**：
- 减少 CPU 占用（busy spin → yield → sleep）
- **但不一定减少 `hw_send_zero` 计数**（spin 次数可能不变，只是每次 spin 之间有间隔）
- 可能让 FIFO 有更多时间排空，从而提高单次 spin 成功率

**风险**：
- 中 — 引入调度延迟，可能影响吞吐
- `sleep` 在内核态需要定时器机制，可能引入复杂度
- QEMU 路径可能退化（QEMU 不需要退避）

**评估**：收益不确定，风险中等，**不作为首选**。

### 方向 D: IER THR_EMPTY 延迟使能

**思路**：只在 FIFO 接近空（如 < 4B）时才使能 THRE IRQ，而非每次 budget exhausted 都 `update_ier(THR_EMPTY)`。

**预期收益**：
- 减少 IRQ 噪音（当前每次 budget exhausted 都 enable THR_EMPTY → 可能造成 IRQ 风暴）
- 提高每次 IRQ 的有效性（IRQ 到达时 FIFO 确实需要填充）

**风险**：
- 高 — 需要修改 IER 使能逻辑
- 需要读取 LSR 判断 FIFO 水位，但 NS16550 LSR 只有 THRE（FIFO 可填充）和 TEMT（完全空），没有"水位"字段
- D1 DW APB UART 可能有不同 LSR 语义
- 可能影响 QEMU 路径

**评估**：风险高，收益不明确，**不在 Q19C.8e 范围内**。

### 方向 E: D1 专用 copier 路径（内联 LSR poll with yield）

**思路**：在 D1 cfg 下，budget exhausted 后做 bounded LSR poll with yield（内联在 copier 中，不需要独立 watchdog）。

**与方向 B 的区别**：
- B 是通用 watchdog（在 uart_16550 crate 内）
- E 是 D1 特化（在 `ArceOsD1UartPort` 或 D1 专用 copier 路径内）

**实现草图**：
- 方案 1：D1 实现 `UartPort::send_bytes_blocking()` 等价方法，内部 bounded poll
- 方案 2：D1 专用 tx_copier_loop 变体，cfg gate 在 `kernel/src/drivers/uart_init.rs`

**预期收益**：
- 与方向 B 相同，但只影响 D1 cfg
- QEMU 路径完全不变

**风险**：
- 低-中 — 只影响 D1 cfg
- 需要在 `uart_16550` crate 暴露 hook，或在 kernel 层覆写 copier
- 可能与方向 A 时间预算组合：D1 路径用更长时间预算 + yield fallback

## 7. 推荐组合：A + B（或 A + E）

### 7.1 推荐方案

**首选**：方向 A（时间预算 1ms）+ 方向 B（通用 LSR poll watchdog）

**理由**：
1. 方向 A 让 budget exhausted 更少发生（1ms 预算能覆盖 FIFO 排空）
2. 方向 B 保证即使 budget exhausted 后 ISR 丢失，也能在 watchdog 周期内恢复
3. 组合后：fast path 仍走 spin（≤1ms），fallback 走 watchdog（bounded yield poll）
4. 两个方向都在 `uart_16550` crate 内，D1/QEMU 共享，但 QEMU 路径不受影响（QEMU 在 spin 期间就成功）

**备选**：方向 A + 方向 E（D1 特化）
- 如果方向 B 在通用层引入复杂度过高，退而用 E 只在 D1 路径加 fallback
- 缺点：D1 和 QEMU copier 路径分叉，维护成本上升

### 7.2 实施顺序建议

1. **先 A**：改 `TX_FAST_RETRY_LIMIT` 从计数 → 时间预算
   - Gate: QEMU benchmark 不退化 + D1 userbench 仍能完整跑完
   - 观察 `hw_send_zero` / `no_progress_budget_exhausted` 变化
   - 如果 A 单独就能显著降低 budget exhausted，可能不需要 B

2. **再 B（如需要）**：在 budget exhausted 路径加 LSR poll watchdog
   - Gate: D1 P99 长尾从 50ms+ 降到 watchdog 周期级别（如 < 5ms）
   - 观察 S21 size=15 的 P99 是否回到合理范围

3. **验证**：Q19B embedded regression 完整通过 + Q19C.8e gated TX debug snapshot 数据对比

### 7.3 不推荐的方向

- **方向 C**（指数退避）：收益不确定，可能影响吞吐
- **方向 D**（IER 延迟使能）：风险高，Q19C.8e 范围外
- **TX_FAST_RETRY_LIMIT=0 + drain TX_WAKER**：已证伪，不得作为默认
