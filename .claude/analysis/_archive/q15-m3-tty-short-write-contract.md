## 1. 探究目标

Q15 M3 的目标不是性能优化，而是修正 TTY 输出路径的契约错误：当前 `TtyWrite::write(&[u8])` 没有返回值，实际写入数被丢弃，`Tty::write_at()` 固定返回 `Ok(buf.len())`。当 TX ring 或 PTY buffer 满时，VFS/sys_write 层会认为全部写入成功，造成 silent data loss。

本次探究回答 6 个问题：

1. 当前短写问题发生在哪条路径？
2. 哪些 trait / impl / 调用点必须同步改？
3. `usize` 短写契约应如何穿透到 VFS？
4. `ldisc` echo 是否需要保留短写结果？
5. M3 与 M1/M2/M4 已落地逻辑有什么耦合？
6. 应如何拆分实施步骤和验证矩阵，降低 breaking change 风险？

## 2. 当前写入链路

用户态 `write(2)` 到串口输出的主要路径如下：

```text
sys_write/sys_writev
  -> FileLike::write
  -> File::write
  -> axfs::File::write
  -> Device/FileNodeOps::write_at
  -> Tty<R, W>::write_at
  -> W: TtyWrite::write
  -> AsyncUartWriter::write / PtyWriter::write
  -> RingBufTx::push / ringbuf::Producer::push_slice
  -> TX copier
  -> UartPort::send_bytes
```

关键点：

| 层级 | 当前行为 | M3 风险 |
|------|----------|---------|
| `sys_write` | 返回 `FileLike::write()` 的字节数 | 会把短写直接暴露给用户态 |
| `File::write` | blocking 文件直接调用 `inner.write()`，非 blocking 走 `poll_io` | 如果 TTY 返回 `Ok(n < len)`，`poll_io` 不会继续等待 |
| `Tty::write_at` | 调用 `self.writer.write(buf); Ok(buf.len())` | 问题核心，谎报完整写入 |
| `AsyncUartWriter::write` | `self.driver.tx.push(buf);` 丢弃返回值 | TX ring 满时丢字节 |
| `PtyWriter::write` | `push_slice(buf)` 后只 warn 丢弃 | PTY 也存在同类契约问题 |
| `ldisc::output_char` | echo 调用 `writer.write(...)` 并忽略结果 | echo 可容忍丢字符，但需要显式决策 |

## 3. 必改接口面

### 3.1 uart_16550 crate

| 项目 | 当前位置 | 当前签名/行为 | M3 目标 |
|------|----------|----------------|---------|
| `TtyWrite` trait | `../uart_16550/src/tty.rs` | `fn write(&self, buf: &[u8]);` | `fn write(&self, buf: &[u8]) -> usize;` |
| `AsyncUartWriter` TTY impl | `../uart_16550/src/async_/device_ops.rs` | 空 buffer return；非空调用 `tx.push(buf)` 丢返回值 | 直接返回 `tx.push(buf)`，空 buffer 返回 0 |
| trait 文档 | `../uart_16550/src/tty.rs` | 允许 buffered or discarded | 改为“返回实际接受字节数”，禁止实现层静默声称成功 |

`embedded_io_async::Write` 已经返回 `Result<usize, Infallible>`，且当前实现已返回 `self.driver.tx.push(buf)`。它不需要签名修改，只需要与新的 `TtyWrite` 契约保持文档一致。

### 3.2 StarryOS

| 项目 | 当前位置 | 当前行为 | M3 目标 |
|------|----------|----------|---------|
| `Tty::write_at` | `kernel/src/pseudofs/dev/tty/mod.rs` | `self.writer.write(buf); Ok(buf.len())` | `Ok(self.writer.write(buf))` |
| `PtyWriter` | `kernel/src/pseudofs/dev/tty/pty.rs` | `push_slice` 返回值只用于 warn | 返回 `push_slice` 的实际字节数；短写日志可保留 |
| `ldisc::output_char` | `kernel/src/pseudofs/dev/tty/terminal/ldisc.rs` | 多处 echo 忽略写入结果 | 继续忽略返回值或显式 `let _ = ...`；文档化 echo best-effort |
| `TtyConfig` 泛型约束 | `kernel/src/pseudofs/dev/tty/terminal/ldisc.rs` | `W: TtyWrite` | 无额外变化，编译器会约束新签名 |

### 3.3 不建议修改的面

| 项目 | 原因 |
|------|------|
| `DeviceOps::write_at` trait | 已经返回 `VfsResult<usize>`，不需要改动公共 VFS trait |
| `File::write` / `poll_io` | M3 是短写契约修正，不是 blocking write 循环语义重构 |
| TX copier | M1/M2/M4 已解决 TX FIFO retry、drain completion、IER owner；M3 不应改 copier 状态机 |
| ring buffer | `RingBufTx::push()` 已返回实际写入数，接口足够 |

## 4. 语义决策

### 4.1 用户态 write 返回短写

M3 应选择“立即返回实际接受字节数”，而不是在 `Tty::write_at` 内循环直到全部写入。

理由：

1. `TtyWrite::write` 是同步非阻塞接口，无法 await ring 空间。
2. `File::write` 对非 blocking 文件已有 `poll_io`，但对 `Ok(n)` 不会继续等待；强行在 TTY 层循环会引入调度和死锁风险。
3. Linux/POSIX 允许 `write()` 返回短写，调用方必须处理返回值。
4. 现阶段目标是“不谎报成功、不静默丢字节”，不是实现“blocking write exact”。

### 4.2 满 ring 时返回 0 还是 WouldBlock

推荐 M3 第一阶段保持最小改动：`Tty::write_at` 返回 `Ok(n)`，包括 `n == 0`。

理由：

| 方案 | 优点 | 风险 |
|------|------|------|
| `Ok(n)` | 最小改动，准确反映 writer 接收数，和 `embedded_io_async::Write` 一致 | blocking `write()` 在 ring 满时可能返回 0，需要用户态处理 |
| `Err(WouldBlock)` when n==0 | 可触发 `poll_io` 等待，语义更接近非阻塞设备 | blocking 文件路径不一定进入 `poll_io`；需要验证 `poll(OUT)` 与 TX ring 空间完全一致 |
| 循环直到全部写入 | 用户态体验最接近传统 TTY | 容易恢复 M4 曾经的调度台阶问题，且需要 async wait 设计 |

后续如果要做 blocking exact write，应作为 M3.1 单独变更：为 TTY OUT readiness 建立“ring has space”语义，并让 blocking 路径通过 `poll_io` 循环推进。

### 4.3 echo 是 best-effort

`ldisc::output_char()` 服务于输入回显，不是用户态 write 的数据完整性路径。推荐显式忽略返回值：

```rust
let _ = self.writer.write(b"\n");
```

这样编译器和读者都会知道 echo 丢失是可接受行为。若未来要保证 echo 完整，应增加 echo 专用缓冲或复用输出队列，而不是在输入处理循环中阻塞。

## 5. M1/M2/M4 耦合分析

| 已完成阶段 | 与 M3 的关系 | M3 注意点 |
|------------|--------------|-----------|
| M1 fast retry | TX copier 更快消耗 ring，降低短写发生概率 | 不要把 M1 性能改善误判为短写问题不存在 |
| M2 TxCompletion | flush/tcdrain 可以确认排空 | M3 后 benchmark 必须继续 `write + tcdrain`，避免只测写入接受数 |
| M4 IER single owner | interrupt enable 由 `UartPort::update_ier()` 管理 | M3 不应重新引入 enable callback 或 CACHED_IER |

M3 的正确性依赖现有 `RingBufTx::push()` 返回值，而不是改变 TX copier。只要 writer 准确返回接受数，M1/M2/M4 可以保持不动。

## 6. 推荐实施计划

### Step 1: 改 uart_16550 trait 契约

修改：

- `../uart_16550/src/tty.rs`
- `../uart_16550/src/async_/device_ops.rs`

验收：

- `cargo check --features async`
- `cargo test --features async`

预期编译失败会暴露 StarryOS 中所有未更新的 `TtyWrite` impl / callsite。

### Step 2: 改 StarryOS 实现者

修改：

- `kernel/src/pseudofs/dev/tty/pty.rs`
- `kernel/src/pseudofs/dev/tty/mod.rs`
- `kernel/src/pseudofs/dev/tty/terminal/ldisc.rs`

建议形态：

| 文件 | 修改 |
|------|------|
| `pty.rs` | `fn write(&self, buf: &[u8]) -> usize { let written = ...; ...; written }` |
| `tty/mod.rs` | `Ok(self.writer.write(buf))` |
| `ldisc.rs` | 对 echo 写入使用 `let _ = self.writer.write(...)` |

### Step 3: 增加 focused tests / witness

优先添加不依赖 QEMU 的单元测试或小型集成测试：

| 测试 | 目标 |
|------|------|
| `PtyWriter` short write | 填满 PTY buffer 后写入大 buffer，断言返回值小于输入长度 |
| `Tty::write_at` short write propagation | 构造小容量 writer 或测试 writer，断言 `write_at` 返回实际接受数 |
| `AsyncUartWriter` TTY impl | 若 crate 内已有 mock ring，可直接断言 `TtyWrite::write` 返回 `RingBufTx::push` 值 |

如果现有测试基础不方便，至少保留 QEMU witness：

1. 写入尺寸覆盖 `1B/15B/16B/17B/32B/49B/64B/4096B`。
2. 记录 `write()` 返回值与 `tcdrain()` 结果。
3. 对大写入增加“总返回字节数累加循环”，避免 benchmark 因短写低估吞吐。

### Step 4: QEMU Manual QA

必须验证：

| 场景 | 期望 |
|------|------|
| Shell 启动 | 无 panic，提示符正常 |
| Shell 交互 | 输入 echo 不阻塞，命令输出正常 |
| FIONBIO | 非阻塞路径仍 PASS |
| benchmark 1B/64B/4096B | 无 10ms 台阶回归 |
| `write + tcdrain` | `tcdrain` 仍等待 M2 四阶段 drain |

## 7. 风险清单

| 风险 | 触发条件 | 缓解 |
|------|----------|------|
| 用户态 benchmark 误读短写 | benchmark 假设单次 write 全部成功 | benchmark 改成循环累计写入直到完成 |
| PTY 行为变化 | 旧代码只 warn 丢弃，新代码返回短写 | 这是正确变化；需要测试覆盖 |
| blocking write 返回 0 | ring 满且 `Ok(0)` 直接穿透 | 先接受为最小修复，后续 M3.1 再评估 WouldBlock/poll_io |
| echo 丢字符更明显 | echo 写入结果被显式忽略 | 文档化 echo best-effort，不把 echo 作为可靠输出路径 |
| 外部 crate API breaking | `TtyWrite` 公共签名改变 | 当前 path dependency 由 StarryOS 同步改；提交需双仓库一致 |

## 8. 建议的完成定义

M3 完成不应只以编译通过为准。建议 Gate：

- `uart_16550`: `cargo check --features async` 通过。
- `uart_16550`: `cargo test --features async` 通过。
- StarryOS: `cargo check -p starry-kernel` 或项目当前等价 check 通过。
- StarryOS: QEMU 启动 + Shell 交互通过。
- benchmark: 写入循环已能处理短写，`write + tcdrain` 无明显退化。
- 文档: `TtyWrite` 注释不再允许“discarded but success unknown”的模糊语义。
