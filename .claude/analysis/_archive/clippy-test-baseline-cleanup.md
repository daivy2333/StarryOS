## 1. 目标与边界

本次分析为后续清理 change 建立可复现基线，回答以下问题：

1. 三个 `unused import` 是真正死代码，还是 feature 边界不完整。

本轮只读取源码、复现命令并生成文档，没有修改 Rust 源码或 Cargo manifest。

## 2. 结论摘要

当前问题不是一个统一的“clippy 失败”，而是五类相互独立的问题：

| 优先级 | 类别 | 当前证据 | 建议处理 |
|--------|------|----------|----------|
| P0 | 内嵌 `uart_16550` manifest 漂移 | 相比 `../uart_16550/Cargo.toml` 缺少 `assert2`、`embedded-io` dependency wiring 和 `resolver = "3"` | 恢复与本地 canonical crate 一致的 manifest 条目 |
| P0 | feature-scoped import | 三个 import 仅在 D1 user/fullbench feature 使用，其他模式产生 warning | 给 import 添加与使用点一致的 `cfg`，不要删除功能代码 |
| P0 | `embedded-io` feature 损坏 | `--all-features` 首个错误为 unresolved import `embedded_io` | 将 feature 改为 `embedded-io = ["dep:embedded-io"]` |
| P1 | lint 作用域泄漏 | `uart_16550` 自动成为 workspace member；其 `deny(clippy::cargo)` 检查 StarryOS sibling package metadata | 明确 workspace membership，隔离可复用 crate 的 lint gate；不要用 blanket allow 掩盖 |
| P1 | kernel host test 拓扑缺失 | `cargo test -p starry-kernel --lib` 因可选 axfs/axnet/display/task-ext 未启用而产生 42 个错误 | 不把裸 host test 当当前 gate；先设计 host-test feature 或抽取纯逻辑测试 |
| P2 | 外部环境 warning | `/home/daivy/.cargo/config` 已弃用 | 在用户级 Cargo 配置中迁移为 `config.toml`，不属于仓库源码 change |

## 3. 三个 unused import

### 3.1 `alloc::vec`

定义位置：`kernel/src/entry.rs:4`。

实际使用点位于：

- `lichee-d1-userbench`：`entry.rs:198`
- `lichee-d1-fullbench`：`entry.rs:281-282`
- `lichee-d1-fullbench-command`：`entry.rs:411-415`

因此它不是死代码。QEMU、D1 smoke 和 D1 kbench 不编译这些使用点，却无条件导入 `vec` 宏，产生 warning。建议把 `vec` 从公共 `use alloc::{...}` 中拆出，并使用：

```rust
#[cfg(any(
    feature = "lichee-d1-userbench",
    feature = "lichee-d1-fullbench",
    feature = "lichee-d1-fullbench-command"
))]
use alloc::vec;
```

### 3.2 `ROOT_FS_CONTEXT` 与 `Mountpoint`

二者只在 `kernel/src/pseudofs/mod.rs:52-57` 的 `init_memory_root()` 使用。该函数同样只为 D1 user/fullbench 三种 feature 编译。

建议保留 `FS_CONTEXT`、`FsContext` 和其他通用 VFS import；只将 `ROOT_FS_CONTEXT` 与 `Mountpoint` 拆成相同 feature 条件下的 import。直接删除会破坏 D1 memory-root 初始化。

## 4. uart_16550 manifest 漂移

仓库内嵌 manifest 与相邻 canonical crate 的差异只有以下三组：

```diff
+resolver = "3"
+embedded-io = { version = "0.7", optional = true }
+[dev-dependencies]
+assert2 = { version = "0.4.0", default-features = false, features = [] }
-embedded-io = []
+embedded-io = ["dep:embedded-io"]
```

这组差异能够直接解释两个主要失败：

- `cargo test --manifest-path crates/uart_16550/Cargo.toml --features async`：17 个 `assert2` unresolved errors。
- `cargo clippy ... --all-features --lib`：`src/embedded_io.rs` 无法解析 `embedded_io`，后续出现 5 个连带 associated-type errors。

这些不是测试源码损坏，而是内嵌复制时没有带全 manifest 契约。优先恢复 manifest parity，比把 `assert2` 改写成标准 `assert!` 或禁用 `embedded-io` feature 更小、更可追溯。

## 5. Clippy 失败分层

### 5.1 可复现矩阵

| 命令 | 结果 | 说明 |
|------|------|------|
| `cargo check --manifest-path crates/uart_16550/Cargo.toml --features async` | PASS | async library 本身可编译；另有用户级 Cargo config deprecation warning |
| `cargo test --manifest-path crates/uart_16550/Cargo.toml --features async` | FAIL | 缺少 `assert2` dev-dependency，17 个 E0433 |
| `cargo clippy --manifest-path crates/uart_16550/Cargo.toml --features async --all-targets -- -D warnings` | FAIL | `assert2`、workspace metadata、duplicate dependency、两个 `missing_const_for_fn` |
| `cargo clippy --manifest-path crates/uart_16550/Cargo.toml --all-features --lib --no-deps` | FAIL | `embedded-io` feature 没有关联 dependency |
| `cargo test --package starry-kernel --lib` | FAIL | host/default feature 组合缺 axfs、axnet、axdisplay、task-ext，共 42 个编译错误 |
| `cargo check --package starryos --features qemu --target riscv64gc-unknown-none-elf` | ENV BLOCK | `lwext4_rust` C 编译在当前受限环境触发 `Bad system call` |

### 5.2 workspace metadata 不是 uart_16550 包自身缺失

根 `Cargo.toml` 虽然只显式列出 `members = ["kernel"]`，Cargo 仍会把 workspace 根包以及 workspace 目录内的 path dependency 自动纳入 members。当前 `cargo metadata` 的成员包括：

- `starryos`
- `starry-kernel`
- `crates/uart_16550`
- `crates/axplat-riscv64-lichee-d1`

`uart_16550/src/lib.rs` 在 crate 级 `deny(clippy::cargo)`，因此对该包执行 clippy 时，`cargo_common_metadata` 也报告 sibling package 的 readme/keywords/categories 缺失。该 lint 边界与可复用驱动 crate 的源码质量无关。

建议后续 change 明确选择一种策略：

1. 推荐：将 `crates/uart_16550` 加入 workspace `exclude`，继续用独立 manifest 命令验证它；StarryOS 仍可通过 path dependency 使用它。
2. 次选：把所有自动成员改成显式成员，并补齐所有 package metadata。
3. 不推荐：删除 `clippy::cargo` 或对全部 lint 使用 `allow`，这会同时丢失真正有价值的 package 检查。

`multiple_crate_versions(bitflags)` 也来自整个 StarryOS workspace lock graph；`cargo tree -p uart_16550 --features async` 的包级依赖图只有 `bitflags 2.13.0`。应先隔离 workspace lint 边界，再判断是否仍需针对性 allow。

### 5.3 两个真实源码 lint

关闭 telemetry 时，以下兼容性 no-op 方法触发 `missing_const_for_fn`：

- `AsyncUartDriver::record_tx_push()`：`driver.rs:314`
- `AsyncUartDriver::reset_tx_debug()`：`driver.rs:324`

它们可以安全评估为 `const fn`；改动前后都没有数据访问或副作用。不要为消除 lint 删除 no-op API，因为该 API 用来保持 telemetry 开关两侧调用面一致。

## 6. 测试 Gate 应按层划分

StarryOS kernel 是 `no_std`、平台/feature 驱动的内核 crate。当前裸 `cargo test -p starry-kernel` 既没有启用可选 FS/network/display 依赖，也没有提供完整平台上下文，所以它不是有效质量 Gate。

当前合理的验证层次是：

| 层 | 目标 | 建议 Gate |
|----|------|-----------|
| 可复用纯 Rust 驱动 | `crates/uart_16550` | host `cargo test` + `cargo clippy --all-targets` + `--all-features` compile |
| kernel feature 编译 | StarryOS QEMU/D1 | 每个受支持 feature 使用对应 target、`PLAT_CONFIG` 和工具链执行 `cargo check/clippy` |
| kernel 纯逻辑测试 | early console 等 | 后续建立最小 host-test feature，避免编译全部平台/VFS/syscall 模块 |
| 系统行为 | IRQ、TTY、rootfs、用户进程 | QEMU boot/benchmark 与真板 smoke，不由 host unit test 替代 |

当前 `kernel/src/platform/early_console.rs` 有 6 个纯逻辑测试，但被整个 kernel crate 的 feature 拓扑挡住。后续可选择抽成小 crate，或增加只编译 platform pure logic 的 host-test target；不建议为了跑这 6 个测试给 host 模式无条件启用所有设备依赖。
