## 1. 结论

当前只保留一个 Q6 真板验证 milestone 已经不适合继续开发。`optimization/spec.md` 中 Q6 同时承载了硬件 bring-up、SMP 内存序修复、U-Boot/PLIC/Clock 验证、DMA 决策、高波特率、死代码治理、远期性能实验等不同性质的工作。它们的触发条件和验证方式不同，放在一个 Q6 下会导致开发顺序不清、Gate 不可执行。

建议把 Q15 之后的工作改成 6 个可独立推进的 milestone：

| 新阶段 | 目标 | 主要条目 | 是否依赖真板 |
|--------|------|----------|--------------|
| **Q16** | 文档与规格收敛 | spec drift、任务重排、基线口径统一 | 否 |
| **Q17** | SMP / 内存序正确性 | O63 | 否，真板复验 |
| **Q18** | 真板观测与 bring-up 工具 | O66、O64/O65 验证脚手架 | 部分 |
| **Q19** | VisionFive2 UART 验证 | O38、O39、Q15 Manual QA 真板复跑 | 是 |
| **Q20** | 吞吐扩展决策 | O3/O40/O69、O41 | 是，依赖 Q19 数据 |
| **Q21** | 维护性清理 | O48/O49/O50、LTO 发布前检查 | 否 |

远期探索 O1/O36、O54/O55、O58/O59、O37 不应进入近期 milestone，建议保留为 **Q22 预研池**，只有在 Q19/Q20 的真板数据证明当前路径不足时才启动。

## 3. 分类原则

后续阶段不应按 O 编号顺序排，而应按 Gate 类型排：

| 类型 | 判定标准 | 示例 |
|------|----------|------|
| **Spec hygiene** | 不改代码，只修正任务/规格/基线口径 | Q16 |
| **QEMU 可验证正确性** | 不需要真板即可改代码并跑 QEMU 回归 | O63 |
| **硬件观测脚手架** | 可以先写日志/探针，但最终 PASS 依赖真板 | O66、O64/O65 |
| **真板 bring-up** | 必须拿到 VisionFive2 才能判定 | O38、O39 |
| **数据驱动决策** | 必须先有真板测量数据，再决定是否做 | O3/O40/O69、O41 |
| **维护性债务** | 不阻塞 bring-up，可独立排期 | O48/O49/O50 |
| **远期实验** | 高成本或会改变架构边界 | O1/O36、O54/O55、O58/O59、O37 |

这个原则继承 Q15 的 L205/L208 经验：先建立可观测基线，再做正确性修复，再做规范化，最后处理契约或架构实验。禁止把多个不同 Gate 的优化一次性塞进同一 milestone。

## 4. 建议 Milestone

### Q16: 文档与规格收敛

**目标**：把 Q15 后的任务体系从“Q6 一个筐”改成可执行 roadmap。

| 任务 | 内容 | Gate |
|------|------|------|
| Q16.1 | 修正 `openspec/project.md` 当前分支 | `git branch --show-current` 与文档一致 |
| Q16.2 | 将 `tasks.md` 的 Q6 拆为 Q17-Q21 候选阶段 | 每个阶段有独立 Gate |
| Q16.3 | 修订 `optimization/spec.md` Q6 章节，把 O63/O64/O66/O3/O40/O41 分流 | `openspec validate --specs` 通过 |
| Q16.4 | 标注或修订 stale capability specs：`async-uart-traits`、`arceos-adapter` | 与 ADR-036/Q15 基线不冲突 |

**建议 OpenSpec change**：`q16-roadmap-rebaseline`

### Q17: SMP / 内存序正确性

**目标**：在真板前先消除 QEMU 单 hart 掩盖的多核 correctness bug。

| 条目 | 内容 | Gate |
|------|------|------|
| O63-P0 | `ArceOsUartPort::update_ier()` 的 `ier_cache` RMW 竞争 | `cargo check` + QEMU benchmark 无退化 |
| O63-P1 | `tx_copier_active` Release/Acquire | QEMU `tcdrain`/flush 回归 |
| O63-P1 | `tx_staged_bytes` AcqRel/Acquire | 短写 + drain benchmark 回归 |
| Q17-extra | 评估 QEMU SMP 配置能否作为预检 | 能跑则加入 CI/Manual QA；不能跑则记录阻塞 |

**当前代码证据**：`kernel/src/drivers/uart_init.rs:105-110` 的 `update_ier()` 仍是 `Relaxed load -> store`，且 RMW 在 `SpinNoIrq` 锁外。`learned/spec.md` L208 已把它标为 Q6 SMP P0 阻塞。

**建议 OpenSpec change**：`q17-smp-memory-order`

### Q18: 真板观测与 bring-up 工具

**目标**：先具备“看见硬件状态”的能力，再做真板修复，避免重复方向 A 的硬件状态误判。

| 条目 | 内容 | Gate |
|------|------|------|
| O66 | `print_preserved_status()` / UART、PLIC、Clock 状态 dump | QEMU 上可编译运行；真板上能输出关键寄存器 |
| O64 | trust u-boot 决策脚手架 | 明确哪些状态只观察、哪些状态允许重初始化 |
| O65 | PLIC init_primary/init_percpu 防御性验证 | 记录当前 axplat crate 路径是否已安全 |
| O71 | PAC 类型安全寄存器访问评估 | 只做决策，不强行引入依赖 |

**边界**：O64 不限制 UART FCR/IER/波特率重新初始化；现有修订已经说明 UART 重新 init 无害。Q18 重点是 PLIC/Clock/SoC 状态，不是改写 async UART 数据通路。

**建议 OpenSpec change**：`q18-vf2-observability`

### Q19: VisionFive2 UART 验证

**目标**：在真板上复跑 Q15 的手动 QA，并把 QEMU 不可信的吞吐量替换为真板数据。

| 条目 | 内容 | Gate |
|------|------|------|
| O38 | VisionFive2 UART 时钟适配 | 串口正常输出，无乱码 |
| O39 | FIFO 深度验证 | FIFO 边界矩阵有真板数据 |
| Q15 QA | 1B latency、64B TX、FIONBIO、tcdrain、Shell 交互 | 全部 PASS，记录到 benchmark report |
| Q19-doc | 更新 `SNAPSHOT.md` / `optimization/spec.md` 真板数据 | 明确 QEMU vs 真板可信度 |

**建议 OpenSpec change**：`q19-vf2-uart-validation`

### Q20: DMA / 高波特率决策

**目标**：用 Q19 数据决定是否值得做 DMA 或高波特率扩展。

| 条目 | 内容 | Gate |
|------|------|------|
| O3/O40/O69 | DMA 控制器和 UART FIFO 可达性决策树 | 有 JH7110 证据；无证据则明确拒绝 |
| O41 | 230400+ 高波特率支持 | 只有在 O38/O39 稳定后实施 |
| Q20-bench | PIO+中断 vs DMA/高波特率收益评估 | 必须有真板数据 |

**建议 OpenSpec change**：`q20-dma-highbaud-decision`

### Q21: 维护性清理

**目标**：处理不阻塞真板验证但会持续增加认知负担的债务。

| 条目 | 内容 | Gate |
|------|------|------|
| O48 | memtrack 是否集成 | Q6 调试需要则启用，否则保留/移除决策 |
| O49 | `ProcessMode::Manual` 移除 | 确认无构造路径后删除 |
| O50 | 预留接口评估 | 超过 90 天未用则移除或留明确注释 |
| ADR-034 | 发布前 LTO 检查 | 开发期不启用，release 前恢复 |

**建议 OpenSpec change**：`q21-maintenance-cleanup`

### Q22: 远期预研池

这些项不进入近期开发队列：

| 条目 | 原因 |
|------|------|
| O1/O36 零拷贝 RX | 安全边界复杂，需 Q19 证明 RX 拷贝是瓶颈 |
| O54 ISR 直接搬运 | 违反当前 ISR 极简取向，需重新评估中断延迟 |
| O55 半满/IDLE 唤醒 | 当前 NAPI 已覆盖相近收益 |
| O58 ArceOS feature gate 特化 | 降低可移植性，只有性能不达标才考虑 |
| O59 MaybeUninit ring buffer | unsafe 成本高，收益不确定 |
| O37 kernel log TX 合并 | 外部 crate 约束强，收益低 |

## 5. 推荐执行顺序

```text
Q16 文档/规格收敛
  -> Q17 SMP 内存序修复
  -> Q18 真板观测工具
  -> Q19 VisionFive2 UART 验证
  -> Q20 DMA / 高波特率决策
  -> Q21 维护性清理
  -> Q22 远期预研池（按真板数据触发）
```

这个顺序的核心理由：

1. Q16 先清理 roadmap，否则后续任务会继续被 Q6 混淆。
2. Q17 不依赖硬件，且 O63 是真板多核最难定位的 P0 风险，应在硬件到位前消除。
3. Q18 先做观测，再做 bring-up，符合 ADR-016/017 的硬件调试教训。
4. Q20 必须等 Q19 数据，不能在 QEMU 上决定 DMA 和高波特率 ROI。
5. Q21 不应阻塞 Q17-Q20，但也不应无限期保留。

## 6. 下一步建议

先不要直接改 `tasks.md` 为最终状态。建议下一步创建一个 OpenSpec change：`q16-roadmap-rebaseline`，内容只做文档与任务重排：

1. 更新 `tasks.md`：把 Q6 拆成 Q17-Q21 候选阶段。
2. 更新 `optimization/spec.md`：按新阶段重排待办，不删除历史 O 编号。
3. 修订或标注 stale capability specs：`async-uart-traits`、`arceos-adapter`。
4. 运行 `openspec validate --specs`。

Q16 通过后，再按 `q17-smp-memory-order` 进入实际代码改动。
