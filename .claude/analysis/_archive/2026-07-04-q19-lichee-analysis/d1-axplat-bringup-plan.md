# D1 AxPlat Bring-up Plan

> Part of StarryOS codebase analysis (branch: `uart-16550-lichee`)
> Generated by openspec-explorer at 2026-06-28
> See also: [lichee-rv-dock-adaptation-plan](lichee-rv-dock-adaptation-plan.md), [platform-parameter-decoupling](platform-parameter-decoupling.md), [lichee/public-platform-notes](lichee/public-platform-notes.md)

## 1. Current Board Result

The latest Lichee RV Dock boot tests have progressed through two distinct blockers.

The earlier test passed the boot image format gate:

- The image is recognized by U-Boot as Android boot image `d1-nezha`.
- The image is loaded from the boot partition and U-Boot prints `Starting kernel ...`.
- The reduced image is small enough for the boot partition after `DWARF=n` (`~410 KiB`, not the earlier `25.6 MiB` debug-heavy image).
- No StarryOS serial output appears after the jump.

That result meant the blocker was no longer "image too large" or "invalid Android boot header". The first root cause was that the payload still used the QEMU axplat boot path.

After Q19a introduced `axplat-riscv64-lichee-d1`, the board result improved:

- U-Boot still recognizes `Android's image name: d1-nezha`.
- U-Boot prints `Starting kernel ...`.
- The payload reaches StarryOS/axruntime far enough to enter `percpu::imp::init`.
- The board then traps with:

```text
Unhandled exception: Store/AMO access fault
EPC: ffffffc040244648 TVAL: ffffffc0402c6908
```

Host-side symbolization showed:

- `EPC 0xffffffc040244648` is `percpu::imp::init`, instruction `amoor.w.aqrl`.
- `TVAL 0xffffffc0402c6908` is the `.bss` symbol `percpu::imp::IS_INIT`.

Therefore the latest blocker is no longer boot image format, load address, or QEMU axplat selection. The current issue is D1/C906 memory attributes in the early DDR page table.

## 2. Root Causes Found

### 2.1 Original root cause: QEMU axplat was still selected

The old `lichee-d1` build still used the QEMU axplat boot path below StarryOS `entry.rs`.

Observed old host-side evidence:

- Android boot image header uses `kernel_addr = 0x40200000`.
- The StarryOS ELF entry is still `0xffffffc080200000`.
- The generated linker script still sets `BASE_ADDRESS = 0xffffffc080200000`.
- `objdump` shows `_stext` calling `axplat_riscv64_qemu_virt::boot::init_boot_page_table` and `axplat_riscv64_qemu_virt::boot::init_mmu`.

Therefore U-Boot loaded the payload at the D1 physical address `0x40200000`, but the linked kernel and the first-stage Rust/assembly boot path were still the QEMU virt platform. The `lichee-d1` feature only changed StarryOS-level platform descriptors and `entry.rs` behavior; it did not replace the lower `axplat` crate that owns `_start`, early page tables, MMU enable, initial console, and the call into `axruntime`.

The current boot chain is:

```text
U-Boot
  -> Android boot payload
  -> axplat::<board>::boot::_start
  -> axplat::call_main
  -> axruntime::rust_main
  -> src/main.rs::main
  -> starry_kernel::entry::init
  -> platform::smoke
```

Because `platform::smoke` is after `axplat` and `axruntime`, an incorrect axplat can fail before the StarryOS smoke code has a chance to print `[starry-d1] early boot`.

This root cause is fixed by the local D1 axplat crate and `MYPLAT` / `PLAT_CONFIG` build wiring.

### 2.2 Current root cause: C906 early DDR PTE attributes

The post-D1-axplat board fault is an AMO fault on normal DDR `.bss`, not a UART or storage error.

The relevant facts:

- Faulting operation: `amoor.w.aqrl` in `percpu::imp::init`.
- Faulting address: high-half `.bss` symbol `percpu::imp::IS_INIT`.
- Platform: Allwinner D1 / T-Head C906 (`xuantie-c9xx` family).

The D1/C906 page table needs T-Head extension bits for normal memory. Project-local `ax-page-table-entry` already encodes this for `xuantie-c9xx`:

```text
SH = 1 << 60
B  = 1 << 61
C  = 1 << 62
SO = 1 << 63
normal memory = SH | B | C
device memory = SH | SO
```

Q19a therefore updates the D1 early boot DDR mappings to use:

```rust
PTE_DDR = 0xef | (1 << 60) | (1 << 61) | (1 << 62)
```

Only DDR identity/high-half mappings should use those cacheable normal-memory bits. Low/MMIO bootstrap mappings must not be blindly marked normal memory.

## 3. Evaluated Approaches

### A. Continue Patching QEMU AxPlat

This is insufficient. Overriding `KERNEL_BASE_PADDR=0x40200000` can change part of the address contract, but the QEMU axplat still owns:

- QEMU-specific `_start` and boot page table setup.
- QEMU memory-map assumptions.
- QEMU console assumptions (`0x10000000`, byte-addressed NS16550).
- QEMU PLIC and MMIO ranges.

This path may produce a smaller or differently linked image, but it does not make the boot path a D1 boot path.

### B. Reuse VisionFive2 AxPlat Directly

VisionFive2 is closer than QEMU for physical memory layout because it also uses a `0x40000000` RAM base and a `0x40200000` kernel physical load address. It is still not a D1 platform:

- It applies VisionFive2-specific hart-id adjustment.
- UART and PLIC facts differ.
- Console implementation still assumes an existing 16550-style abstraction that may not match D1 32-bit register access requirements.

This is useful as a template, not as the final platform crate.

### C. Add Local `axplat-riscv64-lichee-d1`

This is the recommended path.

StarryOS should add a local D1 axplat crate and build the Lichee target through `MYPLAT` / `PLAT_CONFIG`. This aligns with the existing ArceOS/StarryOS layering: `_start`, early page table, MMU setup, early console, memory regions, and platform init belong below StarryOS `entry.rs`.

### D. Minimal Standalone Naked Payload

This remains a useful emergency fallback for proving that U-Boot reaches `0x40200000`, but it does not exercise the real StarryOS runtime. The user chose the proper platform path, so this is not the main plan.

## 4. Recommended D1 AxPlat Design

Create a local crate such as:

```text
crates/axplat-riscv64-lichee-d1/
  Cargo.toml
  axconfig.toml
  build.rs
  src/
    lib.rs
    boot.rs
    console.rs
    init.rs
    mem.rs
    power.rs
    time.rs
    irq.rs
```

Use the existing `axplat-riscv64-qemu-virt` and `axplat-riscv64-visionfive2` crates as structural references, but make D1 facts explicit.

Expected `axconfig.toml` baseline:

```toml
[plat]
arch = "riscv64"
platform = "lichee-d1"
package = "axplat-riscv64-lichee-d1"
family = "riscv64-d1"

[plat.cpu]
num = 1

[plat.mem]
phys-memory-base = 0x4000_0000
phys-memory-size = 0x2000_0000
kernel-base-paddr = 0x4020_0000
kernel-base-vaddr = "0xffff_ffc0_4020_0000"
phys-virt-offset = "0xffff_ffc0_0000_0000"
kernel-aspace-base = "0xffff_ffc0_0000_0000"

[devices]
mmio-ranges = [
    [0x0250_0000, 0x1000],      # UART0
    [0x1000_0000, 0x0400_0000], # PLIC
    [0x0205_0000, 0x1000],      # timer block, optional for initial SBI timer path
]

[devices.uart]
uart-paddr = 0x0250_0000
uart-irq = 18
```

The exact TOML keys should follow the upstream axplat examples, but the facts above are the desired board contract.

## 5. Boot Code Requirements

`boot.rs` should be closer to VisionFive2 than QEMU because D1 RAM starts at `0x40000000`. Required changes:

- Set the physical entry expectation to `0x40200000`.
- Keep the D1 hart id as `0`; do not apply VisionFive2's `hartid - 1` adjustment.
- Preserve the bootloader-provided DTB/FDT pointer (`a1`) even if StarryOS does not parse it yet.
- Build initial page tables for the physical `0x40000000..0x80000000` RAM window and the high-half kernel mapping.
- Call into `axplat::call_main` only after the D1 page table and virtual address transition are correct.

Host verification must show:

```text
ELF entry:        0xffffffc040200000
Linker base:      0xffffffc040200000
Boot image addr:  0x40200000
Boot symbols:     axplat_riscv64_lichee_d1::boot::...
```

The important point is not only the physical load address. The generated symbols must no longer reference `axplat_riscv64_qemu_virt::boot`.

## 6. Console Requirements

D1 UART0 facts collected from public DTS and board probing:

- UART0 base: `0x02500000`
- IRQ: `18`
- compatible: `snps,dw-apb-uart`
- `reg-shift = 2`
- `reg-io-width = 4`
- console baud: `115200`

The initial D1 axplat console should be a polling console with 32-bit MMIO access:

- THR write at `base + 0 * 4`.
- LSR read at `base + 5 * 4`.
- Poll `LSR[5]` before writing.
- Convert `\n` to `\r\n` for readable serial logs.

This console belongs in the D1 axplat crate, not only in `kernel/src/platform/smoke.rs`, because `axruntime` may print before StarryOS `entry::init` runs. If the axplat console is broken, StarryOS-level smoke output may never be visible even if `entry.rs` is correct.

## 7. Build System Plan

Add an optional local dependency in the top-level Cargo manifest:

```toml
[dependencies.axplat-riscv64-lichee-d1]
path = "crates/axplat-riscv64-lichee-d1"
optional = true
features = ["fp-simd"]

[features]
lichee-d1 = [
    "dep:axplat-riscv64-lichee-d1",
    "starry-kernel/lichee-d1",
]
```

The Lichee build should use `MYPLAT` or `PLAT_CONFIG`, not `axfeat/defplat`:

```bash
make ARCH=riscv64 \
  MYPLAT=axplat-riscv64-lichee-d1 \
  PLAT_CONFIG=crates/axplat-riscv64-lichee-d1/axconfig.toml \
  APP_FEATURES=lichee-d1 \
  MEM=512M \
  DWARF=n \
  build
```

Then package the generated binary into Android boot image with:

```text
kernel_addr = 0x40200000
page_size   = 2048
name        = d1-nezha
```

`DWARF=n` is mandatory for boot partition safety unless the linker script is later changed to discard debug sections from the raw binary.

## 8. Verification Gates

### Gate 1: Host Build Artifact

Before flashing:

- `readelf` shows the D1 high-half entry, expected `0xffffffc040200000`.
- Generated linker script has `BASE_ADDRESS = 0xffffffc040200000`.
- `objdump` shows D1 axplat boot symbols, not QEMU axplat symbols.
- Boot image inspect shows `kernel_addr = 0x40200000`.
- Boot image size is safely below the boot partition size (`~10.1 MiB` on the current official image layout).

### Gate 2: First Serial Byte

On the board:

- U-Boot prints `Android's image name: d1-nezha`.
- U-Boot prints `Starting kernel ...`.
- D1 axplat console prints before or during `axruntime`.
- StarryOS eventually prints `[starry-d1] early boot`.

### Gate 3: Failure Localization

If there is still no output:

- Add a temporary ultra-early UART write inside D1 axplat `_start` before MMU enable.
- If pre-MMU output appears but post-MMU output does not, inspect high-half MMIO mapping and `phys_to_virt` usage.
- If no pre-MMU output appears, inspect U-Boot jump address, naked entry layout, instruction set, and UART register access width.

## 9. Milestone Proposal

### Q19a: D1 AxPlat Skeleton

Goal: local `axplat-riscv64-lichee-d1` builds and links.

Exit criteria:

- Build succeeds with `MYPLAT` / `PLAT_CONFIG`.
- Linker base is D1 high-half address.
- `objdump` proves QEMU axplat boot symbols are gone.

### Q19b: D1 AxPlat Polling Console

Goal: board-level polling console works before StarryOS `entry.rs`.

Exit criteria:

- D1 console uses 32-bit MMIO register access.
- Serial output appears from axplat/axruntime or an ultra-early marker.

### Q19c: Android Boot Smoke

Goal: real StarryOS smoke reaches the board.

Exit criteria:

- Android boot image is below boot partition size.
- Board prints `[starry-d1] early boot`.
- The test does not require rootfs, USB, SD/MMC, async TTY, or benchmark workload.

### Q19d: Bring Back Platform Services

Goal: re-enable subsystems one at a time after first-byte success.

Order:

1. SBI timer and timekeeping.
2. PLIC and UART IRQ.
3. Async UART backend for DW APB UART.
4. Minimal filesystem or external test payload route.
5. Benchmark execution path.

## 10. Risks and Non-Goals

Known risks:

- D1 UART requires 32-bit MMIO access; byte-oriented `MmioSerialPort` may not work even with stride 4.
- `axruntime` prints before StarryOS `entry::init`, so an axplat console bug can hide later StarryOS smoke output.
- Current StarryOS descriptor `link_vaddr` must align with the axplat high-half scheme; `0xffffffff40200000` is not the same as `0xffffffc040200000`.
- `DWARF=n` must remain part of Lichee packaging until raw binary size is controlled by linker sections.
- QEMU `axfeat/defplat` must not be used for D1 bring-up.
- D1/C906 final kernel page table may also need `xuantie-c9xx` / T-Head normal-memory flags; fixing the early boot page table does not automatically prove final `axmm` mappings are correct.

Non-goals for the first D1 axplat milestone:

- No USB support.
- No SD/MMC driver.
- No rootfs.
- No async benchmark.
- No UART IRQ dependency before polling output works.
